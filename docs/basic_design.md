## 1. 全体設計方針

### 1.1 設計の前提

要件定義書 1 章・2 章・6 章より、本アプリは以下の性質を持つ。設計はこの性質を前提に、構成要素を最小限に保つ。

| 前提 | 設計への影響 |
|---|---|
| 利用者は 1 名、認証なし | ユーザー識別子をデータモデルに持たない |
| 端末内ローカル保存のみ、同期なし | 競合解決、同期状態、サーバー通信層を持たない。自動バックアップも遮断する（2.10） |
| 全機能オフライン | ネットワーク層、リトライ、キャッシュ戦略を持たない |
| ライトテーマ固定、縦画面固定、日本語のみ | テーマ切替、横向きレイアウト、文字列の多言語化を持たない |
| Android 13 以上 | 通知権限は実行時要求が必要。正確なアラームと共有ストレージ API の前提を確定できる（5.4、9 章） |

### 1.2 アーキテクチャ

単方向データフローの MVVM を採用し、レイヤを 3 層に分ける。

```
[ UI 層 ]  Jetpack Compose の画面 + ViewModel
    │  画面状態（UiState）を購読し、ユーザー操作をイベントとして送る
    ↓
[ ドメイン層 ]  ユースケース + ドメインモデル + 算出ロジック
    │  総ボリューム算出、集計、編集可否判定、タイマー状態遷移
    ↓
[ データ層 ]  Repository + Room（DAO / Entity）+ DataStore + AlarmManager + ファイル出力
```

- 画面状態は ViewModel が保持する単一の `UiState` データクラスとし、Compose 側は状態を描画するだけとする。
- データ層から UI 層へは `Flow` で流す。Room のクエリを `Flow` で購読することで、削除や体重の追加が総ボリューム・グラフ・カレンダーへ即時反映される（要件 4.3.2、4.8）。
- ドメイン層は Android のクラスに依存させない。総ボリューム算出・集計・期間計算は純粋な Kotlin 関数として実装し、単体テストの対象とする。
- 時刻の取得はドメイン層から直接行わず、`TimeProvider`（壁時計・単調時計・当日日付）を注入する。タイマーと日付境界のテストを可能にするため（11 章）。

### 1.3 採用ライブラリ

| 用途 | 採用 | 状態 |
|---|---|---|
| UI | Jetpack Compose（Material 3） | 要件確定 |
| 画面遷移 | Navigation Compose。単一 Activity | 設計確定 |
| DB | Room | 要件確定 |
| 設定値保存 | DataStore（Preferences） | 設計確定 |
| DI | Hilt | 設計確定 |
| タイマー通知 | AlarmManager + NotificationManager | 設計確定（5.4） |
| グラフ | Compose の Canvas による自前描画 | 暫定 / Q-8 |

グラフを自前描画とする理由は、必要な表現が折れ線 2 種に限られること、オフライン専用アプリで外部依存を増やさないことによる。

### 1.4 パッケージ構成案

```

     │   └ csv/                 CSV 生成とファイル書き出し
     ├ domain/
     │   ├ model/               画面・集計で扱うドメインモデル
     │   ├ usecase/             ユースケース
     │   ├ calc/                総ボリューム、集計、期間、編集可否
     │   └ time/                TimeProvider
```

### 1.5 数値型の規約

集計値が 32 ビット整数の範囲を超えるため、型を明示的に定める（設計確定）。

想定最大値は次のとおり。1 セットの最大 = 999.5 kg × 999 回 = 9,985,005（0.1 kg 単位）。想定上限のセット数 15 万件（14 章 M-11）を掛けると約 1.5 × 10^12 となり、`Int` の上限 約 2.1 × 10^9 を大きく超える。

| 値 | Kotlin 側の型 |
|---|---|
| すべての ID | `Long` |
| `epoch_day`、作成日時、経過ミリ秒 | `Long` |
| 重量（0.1 kg 単位）、回数、実施時間、休憩秒 | `Int`（列の値としては範囲内） |
| 重量 × 回数（1 セットの寄与） | `Long` |
| 日別・期間別・部位別の総ボリューム | `Long` |
| SQL の `SUM` 結果 | nullable `Long` |

- 乗算は最初のオペランドから `Long` へ昇格させる（`weightTenthKg.toLong() * reps`）。`Int` 同士で乗じてから代入しない。
- 空集合に対する `SUM` は NULL を返すため、DAO の戻り値を `Long?` とし、Repository で 0 に置き換える。
- kg 単位への変換は表示・CSV 出力の直前にのみ行い、`BigDecimal` で `1/10` を掛ける。途中計算に小数を持ち込まない。

## 2. データ設計

### 2.1 エンティティ関連

```
exercise（種目マスタ）
   ▲ 参照（論理削除のため物理削除しない）
   │
session（セッション）1 ──< exercise_record（種目記録）1 ──< workout_set（セット）
                                    │
                                    └ 有酸素の場合は duration_min を直接保持しセットを持たない

template（テンプレート）1 ──< template_item（テンプレート明細）>── exercise

body_weight（体重記録）  ※ 他エンティティと外部キー関連を持たない
rest_timer（休憩タイマー状態）  ※ 対象セットを参照する 0..1 件
```

### 2.2 共通の設計規約

| 規約 | 内容 | 理由 |
|---|---|---|
| 主キー | すべて `id INTEGER PRIMARY KEY AUTOINCREMENT`、Kotlin 側は `Long` | 種目の同一性は内部 ID で判定する（要件 3.4） |
| 日付 | `epoch_day INTEGER`（1970-01-01 からの日数） | セッション・体重は時刻を持たない。日単位の比較と範囲検索を素直に書ける |
| 日時 | `epoch_millis INTEGER`（UTC ミリ秒） | 作成順の保持にのみ用いる |
| 単調時刻 | `elapsed_millis INTEGER`（`SystemClock.elapsedRealtime()`） | タイマーの経過時間算出に用いる（5.2） |
| 重量・体重 | `0.1 kg 単位の整数`で保持し、列名を `weight_tenth_kg` とする | 浮動小数の誤差を集計に持ち込まない。60.5 kg は 605 |
| 真偽値 | `INTEGER`（0 / 1） | Room の既定 |
| 列挙値 | `TEXT`（2.3 の永続化コード） | Kotlin の列挙子名の変更が DB に波及しないようにする |
| 並び順 | `order_index INTEGER`（0 起点の連番、2.6） | 並び替え要件（4.3.1）に対応 |

重量と体重を同じ 0.1 kg 単位に揃える理由は、入力刻みが重量 0.5 kg・体重 0.1 kg と異なるためである。単位系を揃えることで、自重種目の総ボリューム（体重 × 回数）を整数演算のみで算出できる。

### 2.3 列挙値と永続化コード

Kotlin の列挙子名を直接保存せず、変更しない固定コードを定義する（設計確定）。`TypeConverter` はコードと列挙子を相互変換し、未知のコードを読み込んだ場合は例外を投げる。

| 列挙 | 列挙子 | 永続化コード | 表示名 |
|---|---|---|---|
| `BodyPart` | CHEST | `chest` | 胸 |
| | BACK | `back` | 背中 |
| | LEGS | `legs` | 脚 |
| | SHOULDERS | `shoulders` | 肩 |
| | ARMS | `arms` | 腕 |
| | CORE | `core` | 体幹 |
| | CARDIO | `cardio` | 有酸素 |
| `ExerciseCategory` | STRENGTH | `strength` | 筋トレ |
| | CARDIO | `cardio` | 有酸素 |

- 表示名は UI 層で解決する。DB とビジネスロジックは日本語文字列を持たない。
- 部位の表示順・集計順は要件 4.10 の記載順（胸・背中・脚・肩・腕・体幹・有酸素）とし、列挙子の宣言順で表現する。

### 2.4 テーブル定義

#### 2.4.1 exercise（種目マスタ）

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| name | TEXT | 不可 | 種目名。表示に用いる。最大 50 文字 |
| name_key | TEXT | 不可 | 重複判定用の正規化キー（7.2） |
| body_part | TEXT | 不可 | `BodyPart` の永続化コード |
| category | TEXT | 不可 | `ExerciseCategory` の永続化コード |
| is_bodyweight | INTEGER | 不可 | 自重フラグ。有酸素種目では常に 0 |
| is_deleted | INTEGER | 不可 | 論理削除フラグ（要件 3.4） |
| created_at | INTEGER | 不可 | 作成日時 |
| updated_at | INTEGER | 不可 | 更新日時 |

- インデックス: `is_deleted`
- 条件付き一意索引: `CREATE UNIQUE INDEX idx_exercise_name_key_active ON exercise(name_key) WHERE is_deleted = 0`。「削除されていない種目どうしで種目名が重複しない」という要件 3.2 を DB 側でも担保する。
- Room の `@Index(unique = true)` は条件付き索引を表現できないため、索引は `RoomDatabase.Callback#onCreate` の生 SQL で作成し、以降のスキーマ変更時は `Migration` 内でも同一の SQL を再実行する。索引の存在は Room のスキーマ JSON 差分では検出できないため、インメモリ DB を用いたスキーマテストで「同名の有効種目を 2 件登録すると失敗する」ことを検証する（11 章）。
- Repository でも登録・改名時に重複チェックを行い、UI へは制約違反の例外ではなく検証エラーを返す。
- 物理削除は行わない。削除操作は `is_deleted = 1` の更新とする。

#### 2.4.2 session（セッション）

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| epoch_day | INTEGER | 不可 | 記録日 |
| name | TEXT | 可 | セッション名。最大 50 文字。未入力は NULL |
| created_at | INTEGER | 不可 | 作成日時。同一日内の並び順に用いる |

- インデックス: `epoch_day`
- 同一日に複数件を許容する（要件 3.1）。時刻は持たない。
- 同一日内の並び順は `created_at, id` の昇順とする。`created_at` が同値になった場合も順序が一意に定まるようにする。

#### 2.4.3 exercise_record（種目記録）

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| session_id | INTEGER | 不可 | `session.id` |
| exercise_id | INTEGER | 不可 | `exercise.id` |
| order_index | INTEGER | 不可 | セッション内の並び順 |
| snapshot_name | TEXT | 不可 | 記録時点の種目名 |
| snapshot_body_part | TEXT | 不可 | 記録時点の部位 |
| snapshot_category | TEXT | 不可 | 記録時点の区分 |
| snapshot_is_bodyweight | INTEGER | 不可 | 記録時点の自重フラグ |
| duration_min | INTEGER | 可 | 有酸素の実施時間（分）。筋トレでは NULL |
| created_at | INTEGER | 不可 | 作成日時 |

- インデックス: `session_id`、`exercise_id`
- スナップショット 4 列は要件 3.4 に対応する。過去記録の表示と集計はこの 4 列のみを参照し、`exercise` テーブルを参照しない。
- `exercise_id` は種目別グラフの集計キー（要件 4.9.1）と累計使用回数の集計キー（要件 4.1）として用いる。
- 整合性規約（3 章のライフサイクルにより担保する）。
  - `snapshot_category = cardio` の行は `duration_min` が非 NULL であり、配下に `workout_set` を持たない。
  - `snapshot_category = strength` の行は `duration_min` が NULL である。
  - 未入力・入力途中の種目記録はこのテーブルに存在しない（3.2）。

#### 2.4.4 workout_set（セット）

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| exercise_record_id | INTEGER | 不可 | `exercise_record.id` |
| order_index | INTEGER | 不可 | 種目記録内の並び順 |
| weight_tenth_kg | INTEGER | 可 | 重量（0.1 kg 単位）。自重種目では NULL |
| reps | INTEGER | 不可 | 回数 |

- インデックス: `exercise_record_id`
- 必須項目が揃った時点でのみ行を作成する（要件 4.2）。入力途中のセットは DB に書かない（3 章）。

| set_count | INTEGER | 可 | セット数。有酸素種目では NULL |

- インデックス: `template_id`、`exercise_id`
- テンプレートは種目マスタを直接参照する。スナップショットは持たない。適用時に最新のマスタ属性でスナップショットを作る。
- 種目の削除時、および種目の区分変更時に、該当する `template_item` を物理削除する（要件 3.4、4.6）。この処理は Repository の同一トランザクション内で行い、残った項目の `order_index` を詰め直す（2.6）。
- テンプレート名の重複可否は Q-13 による（暫定: 重複を許す）。

#### 2.4.7 rest_timer（休憩タイマー状態）

計測中のタイマーは 0 件または 1 件のみ存在する（要件 4.4.1）。対象セットとの整合をトランザクションで保証するため、DataStore ではなく Room の単一行テーブルとする。

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー。常に 1 を用いる |
| token | INTEGER | 不可 | タイマーの世代番号。開始のたびに新しい値を採番する（5.5） |
| target_set_id | INTEGER | 不可 | 計測対象のセット |
| started_elapsed_millis | INTEGER | 不可 | 開始時点の `SystemClock.elapsedRealtime()`。経過時間の算出に用いる |
| started_boot_count | INTEGER | 不可 | 開始時点の `Settings.Global.BOOT_COUNT`。端末再起動の判定に用いる（5.2） |
| started_at_millis | INTEGER | 不可 | 開始時点の壁時計時刻。表示・調査用であり、経過時間の算出には用いない |
| target_sec | INTEGER | 不可 | 開始時点の目安秒数 |

- `id` を 1 に固定することで、同時に 1 件のみという要件を DB の主キーで表現する。
- 経過時間は `SystemClock.elapsedRealtime() - started_elapsed_millis` で算出する。壁時計の変更・時刻補正の影響を受けない（5.2）。
- 対象セットが削除された場合、外部キーの CASCADE により行も消える。OS 側のアラームは自動解除されないため、5.5 の手順で別途解除する。

### 2.5 外部キーと削除動作

すべての外部キーを列挙する（設計確定）。Room では `foreignKeys` 属性で宣言し、`PRAGMA foreign_keys = ON` を有効にする。

| 子テーブル | 列 | 親テーブル | ON DELETE | ON UPDATE | 備考 |
|---|---|---|---|---|---|
| exercise_record | session_id | session | CASCADE | NO ACTION | セッション削除で配下を一括削除（要件 4.3.2） |
| exercise_record | exercise_id | exercise | NO ACTION | NO ACTION | 種目は論理削除のため親行が消えない（要件 3.4） |
| workout_set | exercise_record_id | exercise_record | CASCADE | NO ACTION | 種目記録の削除で配下セットを削除 |
| template_item | template_id | template | CASCADE | NO ACTION | |
| template_item | exercise_id | exercise | NO ACTION | NO ACTION | 種目削除時は Repository が明示的に削除（3.5 相当の波及処理） |
| rest_timer | target_set_id | workout_set | CASCADE | NO ACTION | セット削除でタイマー行も消える |

### 2.6 order_index の維持規則

並び順を持つのは `exercise_record`（セッション内）、`workout_set`（種目記録内）、`template_item`（テンプレート内）の 3 つである。以下を共通規則とする（設計確定）。

- 値は 0 起点の連番とし、同一親の中で欠番・重複を作らない。
- 追加は末尾に行い、`order_index = 既存の最大値 + 1` を採番する。
- 削除・並び替えの直後に、同一親の全行へ 0 から連番を振り直す。削除と再採番は同一トランザクションで行う。
- 並び替えは「移動後の並び全体を一括更新する」方式とする。1 行ずつ更新して途中状態で一意性が崩れることを避ける。
- 読み出しのソートキーは `order_index, id` とし、万一値が重複しても表示順が揺れないようにする。
- 登録順で並べる箇所（同一日のセッション、同一日の体重）のソートキーは `created_at, id` とする。

### 2.7 インデックス設計の考え方

想定データ規模（14 章 M-11）では全件走査でも実用速度に収まるが、以下の検索経路には索引を置く。

| 検索経路 | 索引 |
|---|---|
| 日付でセッションを引く（今日の記録、カレンダー、過去記録、CSV） | `session(epoch_day)` |
| セッションから種目記録、種目記録からセットを引く | `exercise_record(session_id)`、`workout_set(exercise_record_id)` |
| 種目 ID で記録を横断集計する（グラフ、累計使用回数） | `exercise_record(exercise_id)` |
| 日付で体重を引く（自重の総ボリューム、体重グラフ、CSV） | `body_weight(epoch_day)` |
| 有効な種目を一覧する | `exercise(is_deleted)` |

### 2.8 初期データ投入

- `RoomDatabase.Callback#onCreate` で、要件 8.1 付録 A の筋トレ種目 53 件を投入する。有酸素種目は投入しない（要件 3.5）。
- 投入順は付録 A の記載順（胸 9 件 → 背中 10 件 → 脚 10 件 → 肩 8 件 → 腕 10 件 → 体幹 6 件）とし、`id` の昇順が付録順と一致するようにする。この順序を初期状態の種目並び順の既定として用いる（14 章 M-6）。
- 投入データはソース内の定数配列として持つ。件数が固定で変更予定がないため。
- `name_key` は投入時に 7.2 の規則で生成する。

### 2.9 マイグレーション方針

- 初回リリースは `version = 1`。破壊的な再作成（`fallbackToDestructiveMigration`）は使用しない。バックアップ手段が CSV 出力しかなく、データ消失を許容できないため。
- 以降のスキーマ変更は必ず `Migration` を記述する。Room のスキーマ JSON をリポジトリに含め、差分をレビュー対象とする。
- 条件付き一意索引（2.4.1）は Room のスキーマ JSON に現れないため、`Migration` 内での再作成と、スキーマテストによる検証を必須とする。
- ジャーナルモードは WAL（Room の既定）を使用する。ただし WAL のみを根拠に読み取りと書き込みの並行実行を保証しない。Room のトランザクション実行制御はバージョンと API に依存するため、CSV 出力側で占有時間を短くする方式を採る（8.8）。

### 2.10 自動バックアップの扱い

要件 2 章「複数端末間でのデータ同期は行わない」および要件 6 章「端末内のみ。外部への送信を行わない」を厳密に満たすため、Android の自動バックアップと端末間転送を無効化する（設計確定）。

| 対象 | 扱い |
|---|---|
| クラウドバックアップ（Auto Backup） | 禁止する |
| 端末間転送（D2D transfer） | 禁止する |
| Room データベースファイル | 対象外とする |
| DataStore の設定値 | 対象外とする |
| タイマー状態 | Room に含まれるため対象外 |
| CSV 出力ファイル | アプリのデータ領域外（ダウンロードフォルダ）のため対象外 |

マニフェストに `android:allowBackup="false"` を指定し、あわせて `android:dataExtractionRules` に以下の規則を与える。`allowBackup` はクラウドバックアップを止めるが、端末間転送は `dataExtractionRules` の側で明示的に除外する必要があるため、両方を指定する。

```xml
<data-extraction-rules>
    <cloud-backup>
        <exclude domain="root" path="." />
        <exclude domain="database" path="." />
        <exclude domain="sharedpref" path="." />
        <exclude domain="file" path="." />
        <exclude domain="external" path="." />
        <exclude domain="device_root" path="." />
        <exclude domain="device_database" path="." />
        <exclude domain="device_sharedpref" path="." />
        <exclude domain="device_file" path="." />
    </cloud-backup>
    <device-transfer>
        <exclude domain="root" path="." />
        <exclude domain="database" path="." />
        <exclude domain="sharedpref" path="." />
        <exclude domain="file" path="." />
        <exclude domain="external" path="." />
        <exclude domain="device_root" path="." />
        <exclude domain="device_database" path="." />
        <exclude domain="device_sharedpref" path="." />
        <exclude domain="device_file" path="." />
    </device-transfer>
</data-extraction-rules>
```

- `exclude` には `domain` と `path` の両方を指定する。`path` を省略した記述は正しい形式ではない。ドメイン全体を対象とする場合は `path="."` とする。
- 端末保護ストレージ（`device_` 接頭辞のドメイン）も除外対象に含める。現時点では該当データを置かない設計だが、将来置いた場合に除外漏れが生じないようにするため。

- `minSdk = 33` のため、Android 11 以前向けの `fullBackupContent` は不要とする。
- 機種変更時のデータ移行手段は CSV 出力のみである。要件 7 章が「CSV 以外のバックアップ・復元」をスコープ外としているため、これを設計上の制約として明記する。

## 3. 記録のライフサイクル

要件 4.2（必須項目が揃うまで保存しない）と、種目記録の作成タイミングを整合させるための設計を定める。本章は基本設計書 v0.1 にあった矛盾（有酸素の `duration_min` 必須と、種目選択時点でのレコード作成の両立不能）を解消するものである。

### 3.1 基本方針

**入力が完了するまで、いかなる記録行も DB に作成しない**（設計確定）。入力途中の内容は ViewModel の下書き状態としてのみ保持する。

この方針を採る理由は次のとおり。

- 要件 4.2 が「必須項目がすべて入力されたセットのみを保存する」「テンプレート適用時に展開される空の入力欄は保存しない」と定めており、下書きを DB に持たない方が要件に忠実である。
- 下書き状態を DB に持つと、`DRAFT` 行を累計使用回数・カレンダー・グラフ・サマリー・CSV のそれぞれで除外する条件が全クエリに必要となり、除外漏れが集計の誤りに直結する。
- 単一利用者・単一端末であり、下書きを他画面や他プロセスと共有する必要がない。

### 3.2 種目記録の生成規則

| 区分 | 生成の契機 | 生成時に書く内容 |
|---|---|---|
| 筋トレ | 配下の最初のセットが「完了」操作で確定した時点 | 種目記録行（スナップショット 4 項目、`duration_min = NULL`）とセット行を同一トランザクションで作成 |
| 有酸素 | 実施時間が入力され「完了」操作が行われた時点 | 種目記録行（スナップショット 4 項目、`duration_min` に入力値） |

- 2 セット目以降は、既存の種目記録に対してセット行のみを追加する。
- 対象セッションが存在しない日に最初の記録を確定した場合、セッションの生成規則は Q-7 による（暫定: セッションが 0 件の日は、記録の確定と同時に無名のセッションを自動生成する）。

#### 3.2.1 適用先セッションの指定

セッションが 0 件の日には、種目選択やテンプレート適用の時点で渡せるセッション ID が存在しない。画面間で受け渡す適用先を、次の型で表現する（設計確定）。

```text
SessionTarget =
    Existing(sessionId: Long)      既存のセッションへ追加する
  | AutoCreateOnCommit             確定時にセッションを生成して、そこへ追加する
```

- S-01 から S-02・S-04 へ遷移する際、対象セッションが特定できる場合は `Existing`、その日のセッションが 0 件の場合は `AutoCreateOnCommit` を渡す。
- `AutoCreateOnCommit` の下書きを確定する際は、セッションの生成と種目記録の作成を同一トランザクションで行う。
- 同一の日に複数の `AutoCreateOnCommit` の下書きがある場合、最初の確定でセッションを 1 件だけ生成し、以降の確定は生成済みのセッションへ追加する。下書きごとにセッションが増えないようにする。
- テンプレート適用でも同じ型を用いる。適用時点では下書きを作るだけであり、セッションは生成しない。

### 3.3 下書き状態

| 項目 | 内容 |
|---|---|
| 保持場所 | 対象画面の ViewModel。`SavedStateHandle` に退避する |
| 生成契機 | 種目選択画面での選択、テンプレートの適用 |
| 内容 | 選択した種目の ID とマスタ属性、筋トレは空のセット入力行（テンプレート適用時は指定セット数分）、有酸素は空の実施時間入力欄 |
| 表示位置 | 対象セッションの確定済み種目記録の後ろに、下書きであることが分かる表示で並べる |
| 破棄契機 | 利用者が下書きを削除した場合、画面を離れた場合、プロセスが終了しタスクからも除去された場合 |
| 永続化 | しない（暫定 / Q-14） |

- `SavedStateHandle` により、画面回転を伴わない一時的なプロセス終了からは復帰できる。タスク一覧からの除去では失われる。
- 下書きの削除に確認ダイアログは出さない。DB 上の記録ではないため、要件 4.3.2 の削除規則の対象外とする。

### 3.4 下書きが各機能へ与える影響

下書きは DB に存在しないため、以下のいずれにも含まれない（設計確定）。この点を明示することで、集計クエリに下書き除外条件が不要であることを保証する。

| 機能 | 下書きの扱い |
|---|---|
| 種目の累計使用回数（要件 4.1） | 含まない |
| カレンダーの実施日判定（要件 4.7） | 含まない |
| 種目別グラフ（要件 4.9.1） | 含まない |
| 期間サマリー（要件 4.10） | 含まない |
| CSV 出力（要件 4.11） | 含まない |
| 過去記録の参照（要件 4.3） | 含まない |
| 当日の総ボリューム表示 | 含まない。確定したセットのみを合計する |

### 3.5 確定後の記録の状態

確定済みの記録は次の不変条件を満たす。Repository のトランザクションで担保し、DB 制約では表現しない。

| 不変条件 | 例外 |
|---|---|
| 有酸素の種目記録は `duration_min` が非 NULL であり、配下にセットを持たない | なし |
| 筋トレの種目記録は `duration_min` が NULL である | なし |
| 筋トレの種目記録は生成時点で 1 件以上のセットを持つ | 全セットを個別に削除した場合、0 セットの種目記録が残る（Q-11） |

0 セットの種目記録が生じるのは、要件 4.3.2 が「セットの削除は該当セットのみを削除する」と定めており、親の種目記録を連鎖削除するとは書かれていないためである。暫定の扱いは次のとおり（暫定 / Q-11）。

| 機能 | 0 セットの種目記録の扱い |
|---|---|
| 今日の記録の表示（当日） | 種目名のみの行として表示し、セットの追加と種目記録の削除の両方を案内する |
| 過去記録の表示（過去日） | 種目名のみの行として表示し、種目記録の削除のみを案内する。過去日への追加は行えないため（暫定 / Q-4） |
| 累計使用回数 | 含める。種目記録は 1 件存在するため（要件 4.1 の定義に従う） |
| カレンダーの実施日判定 | 含めない。セットが 0 件のため（要件 4.7 の定義に従う） |
| 総ボリューム・グラフ・期間サマリー | 寄与しない（合計が 0） |
| CSV 出力 | 出力しない。セット数 0 の行は意味を持たないため |

## 4. ドメインロジック設計

### 4.1 日付と「当日」の判定

- 「当日」は端末のローカルタイムゾーンにおける現在日付とする。編集可否は対象レコードの `epoch_day` と当日の一致で判定する（要件 4.3.1）。
- 画面を開いたまま日付が変わる場合があるため、編集可否は画面表示時に一度だけ判定せず、保存操作の直前にも再判定する。過去日になっていた場合は保存を行わず、スナックバーでその旨を知らせて画面を再読み込みする。
- 休憩タイマーによる `rest_sec` の書き込みは、この編集制限の対象外とする（14 章 M-16）。日付を跨いだ計測でも記録できるようにするため。

### 4.2 期間の定義式

「過去 1 ヶ月」などの自然言語表現を、計算式として確定させる（設計確定。起点の考え方は 14 章 M-20）。`today` は 4.1 の当日とする。

| 期間 | 開始日 | 終了日 | 両端 |
|---|---|---|---|
| 種目別グラフ 1 ヶ月 | `today.minusMonths(1).plusDays(1)` | `today` | 含む |
| 種目別グラフ 3 ヶ月 | `today.minusMonths(3).plusDays(1)` | `today` | 含む |
| 種目別グラフ 1 年 | `today.minusYears(1).plusDays(1)` | `today` | 含む |
| 種目別グラフ 全期間 | その種目の最古の記録日 | `today` | 含む |
| 週サマリー | 対象週の日曜日 | 対象週の土曜日 | 含む |
| 月サマリー | 対象月の 1 日 | 対象月の末日 | 含む |
| CSV 期間指定 | 利用者が選択した開始日 | 利用者が選択した終了日 | 含む（要件 4.11.1） |

- `minusMonths` は月末を丸める。例として 3 月 31 日の 1 ヶ月前は 2 月 28 日（閏年は 29 日）となる。この挙動をそのまま採用し、期間の日数が月によって異なることを許容する。
- 週の始まりは日曜日とする（要件 4.10）。
- サマリーの初期表示は、今日を含む週または当月とする。
- サマリーの前方向への移動は、記録が存在する最古の期間までとする。後方向は今日を含む期間までとし、未来の期間は表示しない。
- グラフの全期間で記録が 1 件もない場合は空状態を表示し、軸を描画しない。

### 4.3 総ボリュームの算出

要件 4.8 に従い、整数演算で算出する。すべて `Long` で計算する（1.5）。

| 種別 | 式（0.1 kg 単位） |
|---|---|
| 筋トレ・自重フラグなし | `Σ (weight_tenth_kg × reps)` |
| 筋トレ・自重フラグあり | `Σ (解決した体重_tenth_kg × reps)` |
| 有酸素 | 算出しない。集計対象外 |

- 判定に用いる自重フラグは `snapshot_is_bodyweight`（記録時点の値）である。
- 算出結果は保存しない。表示・集計のたびに算出する（要件 4.8）。
- 表示桁は 14 章 M-15 による。

#### 4.3.1 自重種目に用いる体重の解決

要件 4.8 の順序をそのまま実装する。

1. 対象日に体重記録があれば、その日の全記録の平均を用いる。
2. なければ、対象日より前で体重記録が存在する直近の日を探し、その日の全記録の平均を用いる。
3. 過去に一度も記録がなければ総ボリュームを 0 とする。

実装上の注意点は次のとおり。

- 対象日より後の記録は参照しない。過去日の総ボリュームが未来の記録で変動しないようにする。
- 平均は `合計(0.1 kg 単位) ÷ 件数` を四捨五入して 0.1 kg 単位の整数に丸める（14 章 M-14）。丸めてから乗算するため、結果は常に整数となる。
- 平均は必ず「その日の全記録」に対して求める。1 日に複数件の記録があるため、代表として 1 件だけを取得してはならない。

期間集計やグラフでは日ごとにこの解決を行う。1 日 1 クエリを繰り返さず、次の 2 回の取得で必要な材料をすべて揃え、メモリ上で走査して解決する。

1. 対象期間内の体重記録を日付昇順で一括取得する。
2. 期間開始日より前で体重記録が存在する最大の `epoch_day` を求め、**その日に属する全記録**を取得する。DAO が日ごとの平均値を直接返す形でもよい。件数を 1 件に限定する取得は行わない。

前方参照を「直近 1 件」としてはならない理由は、直近過去日に複数の体重記録があるとき、1 件だけでは要件 4.8 が求める平均と一致せず、その日以降の自重種目の総ボリュームが誤るためである。

### 4.4 種目の累計使用回数

- 要件 4.1 に従い、`exercise_record` の件数を `exercise_id` ごとに数える。セット数には依存しない。
- 記録の削除で行が消えるため、集計値は自動的に減る。カウンタ列を持たない。
- 種目選択画面の一覧では削除済み種目を除外する。種目別グラフの選択肢では削除済みも扱う（要件 4.9.1）。
- 同数の種目の並び順は 14 章 M-19 による。

### 4.5 期間サマリーの集計

- 期間内の全セットを `snapshot_body_part` ごとに 4.3 の式で合計する（要件 4.10）。
- 部位は記録時点のスナップショットで判定する。マスタの部位を変えても過去の内訳は変わらない。
- 有酸素の種目記録は集計から除外する。
- 部位の内訳は筋トレ 6 部位を常に表示し、値が 0 の部位も 0 として表示する。

### 4.6 種目の削除・区分変更に伴う波及

Repository の単一トランザクションで以下をまとめて実行する。

| 操作 | 波及処理 |
|---|---|
| 種目の削除 | `is_deleted = 1` に更新 → その種目を参照する全 `template_item` を削除 → 各テンプレートの `order_index` を詰め直す |
| 種目の区分変更 | `category` を更新 → その種目を参照する全 `template_item` を削除 → `order_index` を詰め直す |
| 種目名の変更 | `name` と `name_key` を更新。テンプレートと過去記録は変更しない |
| 部位・自重フラグの変更 | マスタのみ更新する |

- いずれの場合も過去の記録行には触れない（要件 3.4）。
- テンプレート内の種目が 0 件になった場合の扱いは 14 章 M-18 による。

## 5. 休憩タイマー設計

### 5.1 状態モデル

タイマーの状態は `rest_timer` テーブルの行の有無で表現する。

| 状態 | 表現 |
|---|---|
| 停止中 | `rest_timer` に行がない |
| 計測中 | `rest_timer` に 1 行あり、経過秒 = `(現在の elapsedRealtime − started_elapsed_millis) ÷ 1000` |

- 表示上の経過秒は 1 秒周期の Flow で再計算する。カウンタ値を保存しない。
- 経過秒が `target_sec` に達した後は計測を終える。表示は `target_sec` で頭打ちとする（要件 4.4.1）。

#### 5.1.1 休憩時間の確定値と上限

要件 4.4.1 は「記録される休憩時間は目安秒数で頭打ちとなる」と定めている。アラームの配信遅延やアプリの復帰遅れにより、実際の経過秒が `target_sec` を上回ることがあるため、休憩時間を書き込むすべての経路で次の共通関数を用いる（設計確定）。

```text
recordedRestSec = min(elapsedSec, targetSec)
elapsedSec      = (現在の elapsedRealtime − started_elapsed_millis) ÷ 1000（切り捨て）
```

この関数を用いる経路は以下のすべてである。個別に経過秒を書き込む実装を作らない。

| 経路 | 記載箇所 |
|---|---|
| 次のセットの完了による旧タイマーの確定 | 5.7 |
| 手動停止 | 5.7 |
| アラーム受信による到達 | 5.5.2 |
| アプリ起動・復帰時の確定 | 5.6 |
| フォアグラウンド監視による到達 | 5.1.3 |

- 手動リセットは休憩時間を書き込まない経路であり、この関数を用いない（要件 4.4.1）。

#### 5.1.2 タイマー完了処理の共通ルーチン

計測中に目安秒数へ到達したことをリアルタイムに検知した場合の完了処理は、検知した経路によらず次の共通ルーチンで行う（設計確定）。対象となるのはフォアグラウンド監視（5.1.3）とアラーム受信（5.5.2）の 2 経路である。アプリ復帰時の事後確定は別の扱いとする（5.6）。

```text
completeRestTimer(token, targetSetId): Boolean
    トランザクション内で以下を行う
        1. rest_timer の行を取得する。行がなければ false を返す。
        2. 行の token と target_set_id が引数と一致するか確認する。
           一致しなければ何もせず false を返す（古い世代、または別のセット）。
        3. 対象セットへ recordedRestSec（5.1.1）を書き込む。
        4. token と target_set_id を条件に rest_timer を削除する。
        5. 削除件数が 1 件なら true、0 件なら false を返す。

    戻り値が true の場合だけ、トランザクションの外で
        6. 終了通知を表示する。
        7. アラームを解除する。
```

削除は、主キーだけでなくトークンと対象セット ID を条件に含める。

```sql
DELETE FROM rest_timer
WHERE id = 1
  AND token = :token
  AND target_set_id = :targetSetId
```

- 取得・確認・書き込み・削除をすべて同一トランザクションに入れる。取得と削除の間に別の操作が割り込む余地を残さない。
- `rest_timer.id` は常に 1 であるため、トークンを条件に含めない削除は、入れ替わった新しいタイマーまで消してしまう。具体的には、完了処理が旧タイマーを読んだ直後に利用者が次のセットを完了すると、旧タイマーが消えて新タイマーが同じ `id` で作られる。その後に完了処理が主キーだけで削除すると、計測を始めたばかりの新タイマーが消える。削除条件にトークンと対象セット ID を含めることで、この取り違えを防ぐ。
- 戻り値によって「どの経路が完了させたか」を一意に決める。フォアグラウンド監視とアラーム受信が同時に走っても、通知は 1 回だけ表示される。
- 通知はアプリの前面・背面を問わず表示する。要件 4.5 は通知バーへの表示を定めており、前面時を除外する規定がないため。
- 通知権限が拒否されている場合は、手順 6 のみを行わない。記録は通常どおり確定する（要件 4.5）。

#### 5.1.3 フォアグラウンド監視の責務

1 秒周期の Flow は表示更新だけでなく、到達の確定も行う（設計確定）。

- 経過秒が `target_sec` 未満の間は、表示の更新のみを行う。
- 経過秒が `target_sec` 以上になった時点で、`completeRestTimer(token, targetSetId)` を呼ぶ。引数には、表示中のタイマー行から読んだ値を渡す。
- アラーム受信と同時に走った場合も、削除に成功した側だけが `true` を受け取り、通知を表示する。

フォアグラウンド監視に確定の責務を持たせる理由は、正確なアラームが使えない状況（5.4 のフォールバック）でも、アプリを見ている限りは目安秒数どおりに確定させるためである。この経路で完了した場合も通知は表示する。アラームが先に解除されるため、`AlarmReceiver` からは通知されないためである。

### 5.2 時刻計算の方式

経過時間の算出には単調増加する `SystemClock.elapsedRealtime()` を用いる（設計確定）。壁時計（`System.currentTimeMillis()`）は用いない。

| 事象 | elapsedRealtime を用いた場合の挙動 |
|---|---|
| 利用者が端末時刻を変更する | 経過時間に影響しない |
| ネットワーク時刻同期による補正 | 経過時間に影響しない |
| タイムゾーンの変更 | 経過時間に影響しない |
| 端末の再起動 | 値が 0 付近へ戻る。ただし再起動の判定には用いない（5.2.1） |

- `started_at_millis`（壁時計）は表示と障害調査のためだけに保持し、経過時間の算出・再起動判定のいずれにも使わない。

#### 5.2.1 端末再起動の判定

再起動の判定には `Settings.Global.BOOT_COUNT` を用いる（設計確定）。この値は端末の起動ごとに 1 ずつ増える整数であり、API 24 以降で読み取れる。特別な権限を必要としない。

- タイマー開始時に現在値を `started_boot_count` へ保存する。
- 起動時・復帰時に現在値と比較し、一致しなければ再起動があったと判定してタイマーを破棄する（5.6）。
- `elapsedRealtime` の大小比較は補助的な判定としてのみ用いる。現在値が `started_elapsed_millis` を下回る場合も再起動とみなす。

`elapsedRealtime` の大小比較だけでは再起動を検出できない場合がある。例えば、端末起動から 30 分後にタイマーを開始し、再起動してから 2 時間後にアプリを開くと、現在値 2 時間が保存値 30 分を上回るため、再起動が起きていないと誤判定する。この状態では、破棄すべきタイマーを「目安秒数に到達済み」と扱い、休憩時間を誤って書き込む。`BOOT_COUNT` の比較はこの取り違えを起こさない。
- アラームは `ELAPSED_REALTIME_WAKEUP` で登録する。壁時計基準（`RTC_WAKEUP`）を使わないことで、時刻変更による早発・遅発を防ぐ。

### 5.3 状態の分離

要件 4.4.2 が挙げる状況に、時計変更を加えて整理する。

| 事象 | 経過時間 | 終了通知 | タイマー行 |
|---|---|---|---|
| アプリ内で別画面へ移動 | 継続する | 発火する | 保持 |
| 他アプリへ切り替える | 継続する | 発火する | 保持 |
| 端末時刻を変更する | 影響を受けない | 影響を受けない | 保持 |
| プロセスのみ終了（タスクは残る） | 復元できる | 発火する | 保持 |
| タスク一覧からアプリを消す | 復元できる | 保証しない | 保持 |
| 端末を再起動する | 継続しない | 発火しない | 起動時に破棄する |

- タスク一覧からの除去では、OS がアプリのアラームを解除する場合がある。要件 4.4.2 が終了通知を保証しないと定めているため、これを許容する。次回起動時に 5.6 の復元処理で休憩時間を確定させる。
- 端末再起動により破棄されたタイマーの対象セットは、休憩時間を空のまま確定する（要件 4.4.2）。

### 5.4 正確なアラーム権限

使用する権限とアラーム API を確定する（設計確定）。

| 項目 | 決定 |
|---|---|
| 宣言する権限 | `android.permission.USE_EXACT_ALARM` のみ |
| 宣言しない権限 | `android.permission.SCHEDULE_EXACT_ALARM` |
| 使用する API | `AlarmManager#setExactAndAllowWhileIdle` |
| アラーム種別 | `ELAPSED_REALTIME_WAKEUP` |
| 事前確認 | `AlarmManager#canScheduleExactAlarms()` |

`USE_EXACT_ALARM` を選ぶ理由は次のとおり。

- 要件 6 章が「タイマーを正確な時刻に発火させるためのアラーム権限を使用する。対象 Android バージョンでは自動付与され、ユーザーへの許可要求を伴わない」と定めている。この記述に該当するのは `USE_EXACT_ALARM` のみである。`SCHEDULE_EXACT_ALARM` は Android 14 以降で新規インストール時に既定で拒否され、利用者による特別なアクセス許可の操作が必要となるため、要件と一致しない。
- 休憩タイマーは本アプリの中核機能であり、その終了通知が唯一の通知用途である（要件 4.5）。
- ストアへ公開せず APK を直接配布するため（要件 1 章）、ストアの審査方針による制約を受けない。
- `minSdk = 33` であり、`USE_EXACT_ALARM` は Android 13 以降で利用できる。

権限が得られない場合の扱いを次のとおり定める。`USE_EXACT_ALARM` は通常権限として自動付与されるため、以下は防御的な処理である。

| 状況 | 動作 |
|---|---|
| `canScheduleExactAlarms()` が false | 正確なアラームを使わず `setAndAllowWhileIdle` で登録する。通知が遅れる可能性がある旨を設定画面に表示する |
| 登録時に `SecurityException` | 例外を捕捉し、同じく `setAndAllowWhileIdle` へ切り替える。タイマー行は削除しない |
| 不正確なアラームも失敗した | タイマー行はそのまま残す。通知は行われないが、次回起動時に 5.6 の復元処理で休憩時間を確定できる |

いずれの場合も、計測と `rest_sec` の記録は通常どおり行う。通知の有無は記録の正しさに影響しない。

### 5.5 DB と AlarmManager の整合

AlarmManager の操作は Room のトランザクションに含められない。両者の不整合を、世代番号（トークン）と冪等な受信処理で吸収する（設計確定）。

#### 5.5.1 トークンと PendingIntent

- タイマーを開始するたびに `token` を新しく採番する。値は乱数による `Long`（`Random.nextLong()` または `UUID` の下位 64 ビット）とする。用途は「同じ世代かどうか」の比較のみであり、大小関係も順序も参照しないため、一意性だけを満たせばよい。単調増加は要求しない。
- `PendingIntent` の `requestCode` は固定値 1 とする。タイマーは同時に 1 件のみのため、固定値にすることで解除操作が常に同じ予約を指す。
- `Intent` の extras に `token` と `target_set_id` を格納する。フラグは `FLAG_UPDATE_CURRENT or FLAG_IMMUTABLE` とし、新しい登録が古い extras を上書きする。

#### 5.5.2 受信時の処理

`BroadcastReceiver` は extras から `token` と `target_set_id` を読み、5.1.2 の共通ルーチン `completeRestTimer(token, targetSetId)` を呼ぶだけとする。判定と書き込みと通知はすべて共通ルーチン側にあり、受信側に固有の処理を持たない。

- 行がない場合、トークンが一致しない場合、対象セット ID が一致しない場合は、いずれも共通ルーチンが `false` を返し、何も起こらない。すでに手動停止・リセット・削除・他経路の完了によって終わっている。
- 対象セット ID を extras に含めて照合する理由は、トークン単独の判定より安全であること、および不具合調査の際にどのセットに対する予約かを追跡できることによる。
- 同じアラームが複数回配信されても結果は変わらない（冪等）。
- 手動停止や前面監視と同時に走った場合も、先にタイマー行を削除した経路だけが通知を表示する。
- 受信処理は DB へのアクセスを伴うため `goAsync()` で実行し、`BroadcastReceiver` の実行時間制限内に完了させる。制限内に完了できなかった場合も、休憩時間は次回起動時の復元処理（5.6）で確定するため失われない。

#### 5.5.3 操作の順序

| 操作 | 順序 | 途中で異常終了した場合 |
|---|---|---|
| 開始 | DB トランザクション（セット作成 → 旧タイマーの確定 → 旧行削除 → 新行作成）→ 旧アラーム解除 → 新アラーム登録 | タイマー行はあるがアラームがない。5.6 の再照合で登録し直す |
| 手動停止・リセット | DB トランザクション（`rest_sec` 書き込みまたは NULL 維持 → 行削除）→ アラーム解除 | アラームが残るが、受信時に 5.5.2 の 1 で何もしない |
| セット・種目記録・セッションの削除 | DB トランザクション（削除、CASCADE で `rest_timer` 行も消える）→ アラーム解除 | 同上 |
| アラーム受信 | 5.5.2 の判定 → DB トランザクション → 通知 | 何もしない。次回起動時に 5.6 が確定させる |

- DB を先に更新し、OS への操作を後に行う。DB を正とし、OS 側の予約は「余分に残っていても害がない」状態に保つ。
- 削除操作では、CASCADE によりタイマー行が消えることを前提にせず、削除前に対象セット ID を取得しておき、削除後に必ずアラーム解除を呼ぶ。

### 5.6 起動時・復帰時の復元と再照合

アプリのプロセス生成時、および `Activity` の `onStart` で以下を実行する。

1. `rest_timer` に行がなければ、念のためアラームを解除して終了する。OS 側に取り残された予約を消すため。
2. 現在の `BOOT_COUNT` が `started_boot_count` と一致しない場合、または現在の `elapsedRealtime` が `started_elapsed_millis` より小さい場合、端末が再起動したと判定する。対象セットの `rest_sec` を NULL のまま行を削除し、アラームを解除する（要件 4.4.2）。
3. 経過秒が `target_sec` 以上であれば、`recordedRestSec`（5.1.1）を書き込んで行を削除し、アラームを解除する。終了通知が発火しなかった場合もここで確定する（要件 4.4.2）。
4. いずれにも当たらなければ計測中として復元し、残り時間でアラームを登録し直す。`requestCode` が固定であるため、既存の予約があれば上書きされ、重複しない。

手順 2 と手順 3 の書き込みと削除は、5.1.2 と同じくトークンと対象セット ID を条件に含め、取得から削除までを同一トランザクションで行う。

復帰時の事後確定では、終了通知を表示しない（設計確定）。理由は次のとおり。

- 要件 4.4.2 は、通知が発火しなかった場合に休憩時間を目安秒数として確定することのみを求めており、後から通知を出すことは求めていない。
- すでに終わった休憩について、時間が経ってから通知を出すと、いま到達したかのように見え、利用者を誤らせる。

したがって、終了通知を表示するのはリアルタイムに到達を検知した 2 経路（フォアグラウンド監視、アラーム受信）に限る。

### 5.7 状態遷移

| 契機 | 処理 |
|---|---|
| セットの完了操作 | セットを確定保存する。計測中のタイマーがあれば、`recordedRestSec`（5.1.1）を対象セットの `rest_sec` へ書き込み、行を削除する。続いて新しいセットを対象とする行を作成し、アラームを登録する（要件 4.4.1） |
| 目安秒数への到達（リアルタイム検知） | 5.1.2 の共通ルーチンを呼ぶ。アラーム受信は 5.5.2、フォアグラウンド監視は 5.1.3 が入口となる。通知を表示する |
| 目安秒数への到達（復帰時の事後確定） | 5.6 の手順 3 で休憩時間のみを確定する。通知は表示しない |
| 手動停止 | `recordedRestSec`（5.1.1）を対象セットの `rest_sec` へ書き込み、行を削除し、アラームを解除する |
| 手動リセット | 対象セットの `rest_sec` を NULL のままとし、行を削除し、アラームを解除する。自動で再開しない（要件 4.4.1） |
| 対象セットの削除 | 5.5.3 の順序で行とアラームを消す |
| アプリ起動・復帰 | 5.6 の処理を行う |

- 最終セットを例外扱いしない。完了操作を行えば必ずタイマーが始まり、停止または到達によって休憩時間が記録される（要件 4.4.3）。
- 有酸素の種目記録は「セットの完了」を持たないため、タイマーの契機とならない。
- 休憩時間の手入力の口は設けない（要件 4.4.3）。

### 5.8 通知

- 通知チャンネルを 1 つ作成する。重要度は音・バイブレーションを伴わない設定とする（要件 4.5）。
- 通知はアプリの前面・背面を問わず表示する。要件 4.5 は通知バーへの表示のみを定めており、アプリが前面にある場合を除外していない。表示の実行は 5.1.2 の共通ルーチンに集約する。
- 通知を出すのは、リアルタイムに到達を検知した場合に限る。アプリ復帰時の事後確定では、休憩時間だけを確定し、遅れた通知は表示しない（5.6）。
- 通知権限が拒否されている場合も、計測と `rest_sec` の記録は通常どおり行う。通知の表示のみを行わない（要件 4.5）。
- 権限の要求は、初回に休憩タイマーが開始した**直後**に行う（設計確定。要件 4.5 は基本設計での決定を認めている）。セットの確定保存とタイマー開始のトランザクション、およびアラーム登録をすべて終えてから、権限要求のダイアログを表示する。
- 要求のためにタイマーの開始を待たせない。要件 4.4.1 が「完了操作を行うとセットが確定保存され、同時に休憩タイマーが自動的に開始する」と定めているため、権限画面を表示している数秒間の計測欠落を許容しない。
- 権限要求の結果は、進行中のタイマーに影響しない。許可された場合は登録済みのアラームがそのまま通知を表示し、拒否された場合は通知のみが出ない。
- 拒否された場合の再要求は行わず、設定画面から OS の設定へ誘導する。

### 5.9 設定値

- 目安秒数はアプリ共通の 1 値とし、DataStore に保存する（要件 4.4.4）。範囲は 1〜3600 秒（要件 3.9）。初期値は 14 章 M-7。
- 計測中に設定値を変更しても、進行中のタイマーには適用しない。`rest_timer.target_sec` が開始時点の値を保持しているため、その値で終了する。

### 6.5 サブフロー

#### 6.5.1 種目の追加・編集

1. 種目名、区分、部位、自重フラグを入力する。
2. 区分を「有酸素」にした場合、部位は「有酸素」に固定し、自重フラグの入力欄を無効化する（暫定 / Q-3）。区分を「筋トレ」にした場合、部位の選択肢から「有酸素」を除く。
3. 保存操作で 7 章の検証を行う。名称の重複は `name_key` で判定する。
4. 編集時に区分を変更した場合、確認ダイアログで「この種目を含むテンプレートから取り除かれる」ことを示す（要件 3.4）。
5. 保存は単一トランザクションで行い、波及処理（4.6）を含める。

#### 6.5.2 テンプレートの作成・編集

1. テンプレート名を入力する。
2. 種目を追加する（S-02 を再利用）。追加した種目が筋トレならセット数を入力し、有酸素ならセット数欄を表示しない。
3. 明細の並び替えと削除を行う。
4. 保存時に名称とセット数を検証する。明細 0 件での新規保存は許可しない（暫定 / Q-12）。
5. 保存後、明細の `order_index` を 0 起点で振り直す。

#### 6.5.3 体重の追加・編集

1. 日付と体重を入力する。日付の既定値は当日とする。
2. 追加は日付を問わず可能。編集は記録日が当日の記録のみ許可し、それ以外では編集の入口を表示しない（暫定 / Q-5）。
3. 削除は日付を問わず可能。確認ダイアログは出さない（要件 4.3.2 の削除単位に含まれないため、体重は即時削除とする。設計確定）。
4. 保存・削除の後、自重種目の総ボリュームが変化することを踏まえ、関連画面は Flow により自動更新される。

#### 6.5.4 通知権限の要求

1. 初回のセット完了で、セットの確定保存・タイマー行の作成・アラーム登録を先に済ませる。タイマーはこの時点ですでに計測を始めている。
2. その直後に、権限の必要性を説明するダイアログを表示する。
3. 利用者が同意した場合のみ OS の権限要求を出す。
4. 許可・拒否のいずれの結果も、進行中のタイマーには影響しない。拒否された場合は再要求せず、計測と休憩時間の記録はそのまま続く（要件 4.5）。
5. 設定画面に、通知が表示されない旨と OS 設定への導線を表示する。

#### 6.5.5 正確なアラームの案内

1. 起動時に `canScheduleExactAlarms()` を確認する。
2. false の場合のみ、設定画面に「終了通知が遅れる場合がある」旨を表示する。
3. ダイアログによる割り込みは行わない。`USE_EXACT_ALARM` は自動付与されるため、通常は発生しない状態である。

#### 6.5.6 CSV 出力の失敗

8.6 に定める。

## 7. 入力値と文字列の規約

### 7.1 数値の範囲

要件 3.9 をそのまま実装する。範囲外・刻み違いの値は保存しない。

| 項目 | 下限 | 上限 | 刻み |
|---|---|---|---|
| 重量 | 0.5 kg | 999.5 kg | 0.5 kg |
| 回数 | 1 回 | 999 回 | 1 回 |
| 有酸素の実施時間 | 1 分 | 999 分 | 1 分 |
| 体重 | 0.1 kg | 999.9 kg | 0.1 kg |
| 休憩タイマーの目安秒数 | 1 秒 | 3600 秒 | 1 秒 |
| テンプレートのセット数 | 1 | 20 | 1（暫定 / Q-12） |

- 検証はドメイン層の純粋関数として実装し、ViewModel と Repository の双方から呼ぶ。
- 入力欄は数値キーボードを既定とし、刻みに合わない値は保存操作の時点でエラーとする。
- 入力文字列から数値への変換は、全角数字と小数点を半角へ正規化してから行う（設計確定）。

### 7.2 文字列の規約

要件 3.10 の最大長に加え、必須・正規化の規則を定める（設計確定）。

| 項目 | 必須 | 最大長 | 空白のみ | 前後空白 |
|---|---|---|---|---|
| 種目名 | 必須 | 50 文字 | 不可 | 除去する |
| セッション名 | 任意 | 50 文字 | 不可（空白のみは未入力として NULL 保存） | 除去する |
| テンプレート名 | 必須 | 50 文字 | 不可 | 除去する |
| セットのメモ | 任意 | 500 文字 | 可 | 除去しない |

- 最大長はコードポイント数で数える。UTF-16 コードユニット数（`String.length`）では、絵文字などで見た目と一致しないため。
- 種目名の重複判定には `name_key` を用いる。`name_key` は「前後空白の除去 → Unicode NFKC 正規化 → 連続する空白を 1 個へ統合 → 小文字化」で生成する。表示用の `name` には利用者の入力（前後空白の除去のみ適用）をそのまま保存する。
- この規則により、`ベンチプレス` と `ベンチプレス`（半角・全角の違い）、`Bench Press` と `bench press` は同一名として扱う。
- テンプレート名の重複は許す（暫定 / Q-13）。`name_key` は持たない。

## 8. CSV 出力設計

### 8.1 出力処理の流れ

1. 画面表示時に、過去の異常終了で残った未完成ファイルを回収する（8.7）。
2. 出力範囲（全期間 / 期間指定）を受け取り、開始日と終了日を検証する。
3. 進捗表示を出し、画面操作を遮断する。
4. 種別ごとに、対象データを一定件数ずつ読み（8.8）、行を組み立てて逐次書き出す。読み取りとファイル書き込みを同一トランザクションに入れない。
5. 3 ファイルすべての書き込みが終わったら結果を表示する（M-8）。
6. 途中で失敗した場合は 8.6 に従う。

### 8.2 ファイル名と文字コード

| 種別 | ファイル名 | 粒度 |
|---|---|---|
| 筋トレ | `strength_YYYYMMDD_HHMMSS.csv` | 種目記録 1 件 = 1 行 |
| 有酸素 | `cardio_YYYYMMDD_HHMMSS.csv` | 種目記録 1 件 = 1 行 |
| 体重 | `weight_YYYYMMDD_HHMMSS.csv` | 記録 1 件 = 1 行 |

- 日時は書き出し実行時のローカル時刻とし、3 ファイルで同一の値を用いる。
- 先頭に UTF-8 BOM（`EF BB BF`）を書く（要件 4.11.1）。
- 改行コードは CRLF とする（暫定 / Q-6）。BOM 付き UTF-8 とあわせ、表計算ソフトでの読み込みを優先する。

### 8.3 書き出し先

- MediaStore の `Downloads` コレクションへ書き出す。保存先を選ばせるダイアログや共有メニューは使わない（要件 4.11.1）。
- ストレージ権限は要求しない（要件 6 章）。
- 書き込み中は `IS_PENDING = 1` を立て、完了後に 0 へ戻す。未完成のファイルが他アプリから見えないようにするため（設計確定）。

### 8.4 エスケープ規則

- カンマ、ダブルクォート、改行のいずれかを含む値はダブルクォートで囲む（要件 4.11.1）。
- 値内のダブルクォートは 2 つ重ねる。
- 日付は `YYYY-MM-DD` 形式で出力する。
- 重量の表記桁は画面表示と同じ規則に揃える（M-4）。

### 8.5 列構成と並び順

| ファイル | 列 |
|---|---|
| 筋トレ | 日付、セッション名、種目、部位、セット数、セット詳細 |
| 有酸素 | 日付、セッション名、種目、実施時間 |
| 体重 | 日付、体重 |

- ヘッダー行は上表の日本語見出しをそのまま出力する。
- セット詳細は `重量x回数` を `; ` で連結する（例: `60x10; 65x8`）。自重種目は重量を省き `x10; x8` とする（要件 4.11.2）。
- 種目名・部位は記録時点のスナップショットを用いる。
- 休憩時間、メモ、総ボリュームは出力しない（要件 4.11.2）。
- 行の並び順は 14 章 M-12 に従う。
- セット数 0 の種目記録は出力しない（3.5）。

### 8.6 例外系

| 事象 | 動作 |
|---|---|
| 開始日が終了日より後 | 実行前の検証でエラーとし、書き出しを開始しない |
| 同一秒の再実行によるファイル名重複 | MediaStore が付与する連番に任せず、`_2`、`_3` の連番を自前で付与して重複を避ける |
| 端末の容量不足、書き込み中の入出力エラー | 当該ファイルの `IS_PENDING` を立てたまま MediaStore のエントリを削除する。未完成のファイルを残さない |
| 3 ファイルの一部のみ失敗 | 成功したファイルはそのまま残す。結果表示で成功したファイル名と失敗した種別を個別に示す |
| MediaStore への登録後、書き込み前に失敗 | エントリを削除する |
| 出力中のデータ変更 | 進捗表示で画面操作を遮断し、利用者による変更を防ぐ。出力中に走り得る唯一の書き込みはタイマーによる `rest_sec` の更新であり、CSV の出力対象外のため内容に影響しない（8.8） |
| 想定最大件数での出力 | 全件をメモリへ展開せず、カーソルで 1 行ずつ読み、1 行ずつ書き出す。筋トレファイルはセット詳細の組み立てのため、種目記録 1 件分のセットのみをメモリに載せる |
| 書き込み中のプロセス強制終了 | 削除処理が走らないため、未完成ファイルが残る。次回の回収処理で削除する（8.7） |

- 出力処理はキャンセル可能とする。キャンセル時は作成済みの未完成ファイルを削除し、完了済みファイルは残す（設計確定）。

### 8.7 未完成ファイルの回収

書き込み中にプロセスが強制終了すると、`IS_PENDING = 1` のエントリが残り、通常の失敗処理では削除されない。次の回収処理を設ける（設計確定）。

- 実行契機は、アプリの起動時と CSV 書き出し画面の表示時とする。
- 自アプリが作成した `Downloads` 配下のエントリのうち、`IS_PENDING = 1` かつ最終更新から一定時間（詳細設計で確定。24 時間を想定）が経過したものを削除する。
- 実行中の出力が作るエントリを消さないよう、経過時間のしきい値で区別する。
- 回収の成否は利用者へ通知しない。失敗しても出力処理は続行する。

### 8.8 タイマー書き込みとの同時実行

想定最大規模の出力では、読み取りが長時間にわたる。その間もアラーム受信やフォアグラウンド監視が `rest_sec` を書き込むため、CSV 出力側が DB を長く占有しない構成にする（設計確定）。

| 項目 | 内容 |
|---|---|
| 読み取り方式 | ページング読み取りとする。日付順のキーで一定件数ずつ取得し、1 回の取得を短いトランザクションで完結させる。3 ファイル全体を 1 つの読み取りトランザクションで囲まない |
| ファイル書き込みの位置 | DB のトランザクションの外で行う。読み取り接続を保持したままファイル入出力を行わない |
| 実行スレッド | CSV 出力は専用のディスパッチャで実行し、UI とタイマーの処理を止めない |
| 待機の許容 | ページ単位の読み取りとタイマーの書き込みが競合した場合、いずれかが短時間待つことを許容する。待ち時間はページ 1 回分の読み取りに限られる |
| 受信側の保護 | `BroadcastReceiver` は `goAsync()` で実行する。万一実行時間制限内に完了しなかった場合も、休憩時間は次回起動時の復元処理（5.6）で確定するため失われない |
| 記録される値 | 書き込みが遅れても `recordedRestSec`（5.1.1）は `target_sec` で頭打ちとなるため、遅延によって記録値が誤ることはない |
| 出力内容 | タイマーが書き込む `rest_sec` は CSV の出力対象外（要件 4.11.2）であるため、出力中に更新されても内容に影響しない |

v0.3 では 3 ファイル分の読み取りを 1 つの長い読み取りトランザクションで囲み、WAL を根拠に「タイマーの書き込みは待たされない」としていた。この前提は撤回する。WAL を有効にしても、Room のバージョンとトランザクション実行 API によっては読み取りと書き込みが直列化され、並行実行が保証されないためである。上記のページング方式は、Room のトランザクション実行制御に依存せず、占有時間そのものを短くする。

- 採用する Room のメジャーバージョンと読み取り接続の API は、10.1 の版数固定に含めて詳細設計で確定する。読み取り接続と書き込み接続を分離する API を採用する場合も、接続を保持したままファイル入出力を行わない構成は変えない。
- 「想定最大件数の CSV 出力中に休憩タイマーが目安秒数へ到達する」組み合わせを結合試験で確認する（11.2）。

## 9. 権限とシステム連携

| 権限 / 連携 | 用途 | 扱い |
|---|---|---|
| `POST_NOTIFICATIONS` | 休憩タイマーの終了通知 | 実行時に要求する。拒否時も計測と記録は継続する（5.8） |
| `USE_EXACT_ALARM` | タイマー終了時刻での正確な発火 | Android 13 以上で自動付与される。利用者への許可要求を伴わない（5.4） |
| MediaStore Downloads | CSV の書き出し | ストレージ権限は要求しない（8.3） |

- `SCHEDULE_EXACT_ALARM`、`RECEIVE_BOOT_COMPLETED`、ネットワーク関連の権限は宣言しない。
- 再起動後のタイマー復元は行わないため、起動完了ブロードキャストの受信は不要である（要件 4.4.2）。
- 外部への送信を行わないことを、権限の非宣言とバックアップの無効化（2.10）の両面で担保する。

### 10.1 SDK の固定値とライブラリのバージョン方針

通知権限、バックアップ、アラーム API、Room の並行処理はいずれもバージョンに依存する。「開発時点の最新」という指定を廃し、SDK は数値で固定し、ライブラリは採用するメジャー系列を定める（設計確定）。

| 項目 | 本書での決定 | 種別 | 根拠 |
|---|---|---|---|
| `minSdk` | 33 | 固定値 | 要件 1 章「Android 13 以上」 |
| `targetSdk` | 35 | 固定値 | 通知権限・正確なアラーム・共有ストレージの挙動を、この版数の仕様に固定する |
| `compileSdk` | 35 | 固定値 | `targetSdk` と揃える |
| Kotlin | 2.0 系 | メジャー系列 | Compose コンパイラが Kotlin 本体に統合された版数を用いる |
| AGP | 8 系 | メジャー系列 | Kotlin 2.0 系との組み合わせ実績による |
| Compose | BOM で一括管理 | メジャー系列 | 個別ライブラリの版数差による不整合を避ける |
| Room | 2 系 | メジャー系列 | 8.8 のページング方式は Room 2 系のトランザクション実行制御を前提とする |
| Hilt | 2 系 | メジャー系列 | |

- 「メジャー系列」の項目は、完全なバージョン番号を詳細設計で決定する。決定した値は `libs.versions.toml` に記述し、そこを唯一の情報源とする。Compose BOM の版数もここで確定させる。
- 本書は上表のメジャー系列を超える変更を「設計の前提が変わる変更」として扱う。同一系列内のマイナー版・パッチ版の更新は詳細設計と実装の判断でよい。
- Room 3 系を採用する場合、読み取り接続と書き込み接続の分離が可能になるため、8.8 の方式を見直す。採用の可否は詳細設計の判断とし、変更する場合は本書へ反映する。
- `targetSdk` を引き上げる場合、5.4（正確なアラーム）、5.8（通知）、2.10（バックアップ）、8.3（共有ストレージ）への影響を再確認する。

## 11. テスト方針

### 11.1 テストの種類

| 対象 | 方法 |
|---|---|
| 総ボリューム算出、体重解決、期間計算、入力検証、`name_key` 生成、CSV 行生成 | 純粋関数の単体テスト |
| DAO とトランザクション（種目削除のテンプレート波及、`order_index` の再採番、CASCADE） | Room のインメモリ DB を用いたテスト |
| 条件付き一意索引 | インメモリ DB で「同名の有効種目を 2 件登録すると失敗する」ことを検証する |
| Room マイグレーション | スキーマ JSON を用いた移行テスト（version 2 以降を作成した時点から） |
| タイマーの状態遷移 | `TimeProvider` を注入した単体テスト |
| 集計値の型 | 想定最大規模のデータで `Int` の範囲を超えることを確認する回帰テスト |
| 画面 | 主要導線に絞った Compose UI テスト |

### 11.2 試験マトリクス

以下の組み合わせを結合試験の観点として定める。

| 観点 | 水準 |
|---|---|
| Android バージョン | 13、14、15 以降のいずれか 1 つ |
| 通知権限 | 許可 / 拒否 |
| 正確なアラーム | 利用可 / `canScheduleExactAlarms()` が false |
| アプリの状態遷移 | 画面内遷移 / 他アプリへ切替 / プロセス終了 / タスク一覧から除去 / 端末再起動 |
| 再起動の間隔 | 再起動直後にアプリを開く / 再起動から数時間後に開く（`BOOT_COUNT` 判定の確認、5.2.1） |
| 端末時計 | 変更なし / 進める / 戻す |
| タイマー | 単独計測 / 多重開始 / 手動停止 / 手動リセット / 対象セットの削除 / 目安秒数を超える遅延配信（上限丸めの確認、5.1.1） |
| リアルタイム到達の経路 | フォアグラウンド監視 / アラーム受信。いずれも通知が 1 回だけ表示されること（5.1.2） |
| 到達時のアプリ状態 | 前面 / 背面。いずれでも通知が表示されること（5.1.2） |
| 復帰時の事後確定 | 休憩時間が目安秒数で確定し、遅れた通知が表示されないこと（5.6）。通知の試験からは分離して判定する |
| 完了処理の競合 | 完了処理の途中で次のセットを完了させ、新しいタイマーが削除されないこと（5.1.2） |
| 通知権限 | 初回タイマー開始直後の要求で、許可・拒否のいずれでもタイマーが止まらないこと |
| 記録操作 | 下書きのまま画面を離れる / セット確定 / 全セット削除 / 種目記録削除 / セッション削除 |
| 日付 | 通常 / 計測中に日付を跨ぐ / 画面表示中に日付が変わる |
| CSV | 正常 / 0 件 / 容量不足 / 同一秒の再実行 / 出力中のキャンセル / 想定最大件数 / 書き込み中のプロセス強制終了と次回の回収（8.7） / 出力中にタイマーが目安秒数へ到達（8.8） |
| 体重 | 直近過去日の記録が 1 件 / 同一日に複数件（平均が使われることの確認、4.3.1） |
| 種目マスタ | 名称変更 / 部位変更 / 自重フラグ変更 / 区分変更 / 削除 / 同名再登録 |

- タイマーと通知の観点は、要件 4.4.2 の保証範囲の表と対応させて合否を判定する。保証しないと定めた組み合わせは、通知の不発を不合格としない。

## 12. 主要な処理のトランザクション境界

| 処理 | 同一トランザクションで行うこと | トランザクション外の後続処理 |
|---|---|---|
| 筋トレの初回セット確定 | 種目記録の作成 → セットの作成 → 既存タイマーの確定と行削除 → 新タイマー行の作成 | 旧アラーム解除 → 新アラーム登録 |
| 筋トレの 2 セット目以降 | セットの作成 → 既存タイマーの確定と行削除 → 新タイマー行の作成 | 同上 |
| 有酸素の確定 | 種目記録の作成（`duration_min` 付き） | なし |

| CSV 出力 | ページ 1 回分の読み取りのみをトランザクションとする。ファイル書き込みはトランザクションの外で行う（8.8） | ページごとの行の書き出し、ファイルの確定（`IS_PENDING` の解除） |
