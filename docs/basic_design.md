## 1. 全体設計方針

### 1.1 設計の前提

要件定義書 1 章・2 章・6 章より、本アプリは以下の性質を持つ。設計はこの性質を前提に、構成要素を最小限に保つ。

| 前提 | 設計への影響 |
|---|---|
| 利用者は 1 名、認証なし | ユーザー識別子をデータモデルに持たない |
| 端末内ローカル保存のみ、同期なし | 競合解決、同期状態、サーバー通信層を持たない |
| 全機能オフライン | ネットワーク層、リトライ、キャッシュ戦略を持たない |
| ライトテーマ固定、縦画面固定、日本語のみ | テーマ切替、横向きレイアウト、文字列リソースの多言語化を持たない |
| Android 13 以上 | 通知権限は実行時要求が必要。共有ストレージ API を前提にできる |

### 1.2 アーキテクチャ

単方向データフローの MVVM を採用し、レイヤを 3 層に分ける。

```
[ UI 層 ]  Jetpack Compose の画面 + ViewModel
    │  画面状態（UiState）を購読し、ユーザー操作をイベントとして送る
    ↓
[ ドメイン層 ]  ユースケース + ドメインモデル + 算出ロジック
    │  総ボリューム算出、集計、編集可否判定、タイマー状態遷移
    ↓
[ データ層 ]  Repository + Room（DAO / Entity）+ DataStore + ファイル出力
```

- 画面状態は ViewModel が保持する単一の `UiState` データクラスとし、Compose 側は状態を描画するだけとする。
- データ層から UI 層へは Kotlin の `Flow` で流す。Room のクエリを `Flow` で購読することで、削除や体重の追加が総ボリューム・グラフ・カレンダーへ即時反映される（要件 4.3.2、4.8）。
- ドメイン層は Android のクラスに依存させない。総ボリューム算出や集計は純粋な Kotlin 関数として実装し、単体テストの対象とする。

### 1.3 採用ライブラリ

| 用途 | 採用 | 補足 |
|---|---|---|
| UI | Jetpack Compose（Material 3） | 要件 6 章で確定 |
| 画面遷移 | Navigation Compose | 単一 Activity + Composable 遷移 |
| DB | Room | 要件 6 章で確定 |
| 設定値保存 | DataStore（Preferences） | 休憩タイマーの目安秒数など少数のキー値 |
| DI | Hilt | ViewModel と Repository の結線 |
| タイマー通知 | AlarmManager + NotificationManager | 要件 6 章の「アラーム権限」の記載に対応 |
| グラフ | 詳細設計で選定（12 章 Q-8 参照） | 折れ線グラフ 2 種のみで足りる |

### 1.4 パッケージ構成案

```
app/
 └ src/main/java/<package>/
     ├ MainActivity.kt
     ├ di/                      Hilt モジュール
     ├ data/
     │   ├ db/                  AppDatabase, Entity, DAO, Converter, 初期データ投入
     │   ├ datastore/           設定値、タイマー状態の永続化
     │   ├ repository/          各 Repository 実装
     │   └ csv/                 CSV 生成とファイル書き出し
     ├ domain/
     │   ├ model/               画面・集計で扱うドメインモデル
     │   ├ usecase/             ユースケース
     │   └ calc/                総ボリューム、集計、編集可否、タイマー算出
     ├ ui/
     │   ├ theme/               ライトテーマ定義
     │   ├ component/           共通 UI 部品
     │   ├ navigation/          遷移定義
     │   └ screen/              画面ごとに Screen と ViewModel を配置
     └ notification/            通知チャンネル、通知の組み立て、アラーム受信
```

## 2. データ設計

### 2.1 エンティティ関連

```
exercise（種目マスタ）
   ▲ 参照（論理削除のため物理削除しない）
   │
session（セッション）1 ──< exercise_record（種目記録）1 ──< workout_set（セット）
                                    │
                                    └ 有酸素の場合は duration_min を直接保持しセットを持たない

template（テンプレート）1 ──< template_item（テンプレート明細）>── exercise

body_weight（体重記録）  ※ 他エンティティと外部キー関連を持たない
rest_timer（休憩タイマー状態）  ※ 対象セットを参照する 0..1 件
```

### 2.2 共通の設計規約

| 規約 | 内容 | 理由 |
|---|---|---|
| 主キー | すべて `id INTEGER PRIMARY KEY AUTOINCREMENT` | 種目の同一性は内部 ID で判定する（要件 3.4） |
| 日付 | `epoch_day INTEGER`（1970-01-01 からの日数） | セッション・体重は時刻を持たない。日単位の比較と範囲検索を素直に書ける |
| 日時 | `epoch_millis INTEGER`（UTC ミリ秒） | 作成順の保持にのみ用いる |
| 重量・体重 | `0.1 kg 単位の整数`で保持 | 浮動小数の誤差を集計に持ち込まない。重量 60.5 kg は 605、体重 62.3 kg は 623 |
| 真偽値 | `INTEGER`（0 / 1） | Room の既定 |
| 列挙値 | `TEXT`（列挙子名） | DB を直接読んだときの可読性を優先する |
| 並び順 | `order_index INTEGER`（0 起点の連番） | 並び替え要件（4.3.1）に対応 |

重量を 0.1 kg 単位で持つ理由は、入力刻みが重量 0.5 kg・体重 0.1 kg と異なるためである。両者を同じ単位系に揃えることで、自重種目の総ボリューム（体重 × 回数）を整数演算のみで算出できる。

### 2.3 列挙値

| 列挙 | 値 | 対応要件 |
|---|---|---|
| `BodyPart` | `CHEST`, `BACK`, `LEGS`, `SHOULDERS`, `ARMS`, `CORE`, `CARDIO` | 3.3 の 7 区分 |
| `ExerciseCategory` | `STRENGTH`, `CARDIO` | 3.2 の区分 |

- 部位の日本語表示名（胸・背中・脚・肩・腕・体幹・有酸素）は UI 層で列挙値から解決する。DB には日本語を保存しない。
- 集計・並び順で用いる部位の表示順は、要件 4.10 の記載順（胸・背中・脚・肩・腕・体幹）に従い、列挙子の宣言順で表現する。

### 2.4 テーブル定義

#### 2.4.1 exercise（種目マスタ）

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| name | TEXT | 不可 | 種目名。最大 50 文字 |
| body_part | TEXT | 不可 | `BodyPart` |
| category | TEXT | 不可 | `ExerciseCategory` |
| is_bodyweight | INTEGER | 不可 | 自重フラグ。有酸素種目では常に 0 |
| is_deleted | INTEGER | 不可 | 論理削除フラグ（要件 3.4） |
| created_at | INTEGER | 不可 | 作成日時 |
| updated_at | INTEGER | 不可 | 更新日時 |

- インデックス: `is_deleted`（種目一覧の抽出用）
- 一意制約: 「削除されていない種目どうしで種目名が重複しないこと」（要件 3.2）。Room の `@Index(unique = true)` は条件付き一意索引を表現できないため、`RoomDatabase.Callback` の `onCreate` で `CREATE UNIQUE INDEX idx_exercise_name_active ON exercise(name) WHERE is_deleted = 0` を発行する。あわせて Repository でも登録・改名時に重複チェックを行い、UI へエラーを返す。
- 物理削除は行わない。削除操作は `is_deleted = 1` の更新とする。

#### 2.4.2 session（セッション）

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| epoch_day | INTEGER | 不可 | 記録日 |
| name | TEXT | 可 | セッション名。最大 50 文字。未入力は NULL |
| created_at | INTEGER | 不可 | 作成日時。同一日内の並び順に用いる |

- インデックス: `epoch_day`
- 同一日に複数件を許容する（要件 3.1）。時刻は持たない。

#### 2.4.3 exercise_record（種目記録）

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| session_id | INTEGER | 不可 | `session.id`。ON DELETE CASCADE |
| exercise_id | INTEGER | 不可 | `exercise.id`。ON DELETE NO ACTION（論理削除のため参照は切れない） |
| order_index | INTEGER | 不可 | セッション内の並び順 |
| snapshot_name | TEXT | 不可 | 記録時点の種目名 |
| snapshot_body_part | TEXT | 不可 | 記録時点の部位 |
| snapshot_category | TEXT | 不可 | 記録時点の区分 |
| snapshot_is_bodyweight | INTEGER | 不可 | 記録時点の自重フラグ |
| duration_min | INTEGER | 可 | 有酸素の実施時間（分）。筋トレでは NULL |
| created_at | INTEGER | 不可 | 作成日時 |

- インデックス: `session_id`、`exercise_id`
- スナップショット 4 列は要件 3.4 に対応する。過去記録の表示と集計はこの 4 列のみを参照し、`exercise` テーブルを参照しない。
- `exercise_id` は種目別グラフの集計キー（要件 4.9.1）と累計使用回数の集計キー（要件 4.1）として用いる。
- 整合性規約: `snapshot_category = CARDIO` の行は `duration_min` が非 NULL かつ配下の `workout_set` を持たない。`STRENGTH` の行は `duration_min` が NULL。DB 制約ではなく Repository で担保する。

#### 2.4.4 workout_set（セット）

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| exercise_record_id | INTEGER | 不可 | `exercise_record.id`。ON DELETE CASCADE |
| order_index | INTEGER | 不可 | 種目記録内の並び順 |
| weight_dg | INTEGER | 可 | 重量（0.1 kg 単位）。自重種目では NULL |
| reps | INTEGER | 不可 | 回数 |
| rest_sec | INTEGER | 可 | 休憩時間（秒）。タイマー未使用・リセット時は NULL |
| memo | TEXT | 可 | メモ。最大 500 文字 |
| created_at | INTEGER | 不可 | 作成日時 |

- インデックス: `exercise_record_id`
- 必須項目が揃った時点でのみ行を作成する（要件 4.2）。入力途中のセットは DB に書かず、ViewModel の状態としてのみ保持する。

#### 2.4.5 body_weight（体重記録）

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| epoch_day | INTEGER | 不可 | 記録日 |
| weight_dg | INTEGER | 不可 | 体重（0.1 kg 単位） |
| created_at | INTEGER | 不可 | 作成日時。同一日内の並び順に用いる |

- インデックス: `epoch_day`
- 1 日に複数件を許容する（要件 3.8）。

#### 2.4.6 template / template_item（テンプレート）

template

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| name | TEXT | 不可 | テンプレート名。最大 50 文字 |
| created_at | INTEGER | 不可 | 作成日時 |
| updated_at | INTEGER | 不可 | 更新日時 |

template_item

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー |
| template_id | INTEGER | 不可 | `template.id`。ON DELETE CASCADE |
| exercise_id | INTEGER | 不可 | `exercise.id` |
| order_index | INTEGER | 不可 | テンプレート内の並び順 |
| set_count | INTEGER | 可 | セット数。有酸素種目では NULL |

- インデックス: `template_id`、`exercise_id`
- テンプレートは種目マスタを直接参照する。スナップショットは持たない。適用時に最新のマスタ属性でスナップショットを作る。
- 種目の削除時、および種目の区分変更時に、該当する `template_item` を物理削除する（要件 3.4、4.6）。この処理は Repository の同一トランザクション内で行う。
- 部位・種目名・自重フラグの変更ではテンプレートを変更しない。

#### 2.4.7 rest_timer（休憩タイマー状態）

計測中のタイマーは 0 件または 1 件のみ存在する（要件 4.4.1）。DataStore ではなく Room の単一行テーブルとして持ち、対象セットとの整合をトランザクションで保証する。

| 列 | 型 | NULL | 内容 |
|---|---|---|---|
| id | INTEGER | 不可 | 主キー。常に 1 を用いる |
| target_set_id | INTEGER | 不可 | 計測対象のセット。ON DELETE CASCADE |
| started_at_millis | INTEGER | 不可 | 開始時刻（UTC ミリ秒） |
| target_sec | INTEGER | 不可 | 開始時点の目安秒数 |
| boot_base_millis | INTEGER | 不可 | 開始時点の起動基準時刻。再起動検知に用いる |

- `boot_base_millis` は `System.currentTimeMillis() - SystemClock.elapsedRealtime()` を保存する。アプリ起動時に再計算した値と一定の誤差を超えて食い違う場合、端末が再起動したと判定してタイマー行を削除する（要件 4.4.2）。
- 対象セットが削除された場合、CASCADE によりタイマー行も消える。

### 2.5 インデックス設計の考え方

想定データ規模（11 章 M-11 案）では全件走査でも実用速度に収まるが、以下の検索経路には索引を置く。

| 検索経路 | 索引 |
|---|---|
| 日付でセッションを引く（今日の記録、カレンダー、過去記録） | `session(epoch_day)` |
| セッションから種目記録、種目記録からセットを引く | `exercise_record(session_id)`、`workout_set(exercise_record_id)` |
| 種目 ID で記録を横断集計する（グラフ、累計使用回数） | `exercise_record(exercise_id)` |
| 日付で体重を引く（自重の総ボリューム、体重グラフ） | `body_weight(epoch_day)` |

### 2.6 初期データ投入

- `RoomDatabase.Callback` の `onCreate` で、要件 8.1 付録 A の筋トレ種目 53 件を投入する。有酸素種目は投入しない（要件 3.5）。
- 投入順は付録 A の記載順（胸 9 件 → 背中 10 件 → 脚 10 件 → 肩 8 件 → 腕 10 件 → 体幹 6 件）とし、`id` の昇順が付録順と一致するようにする。この順序は初期状態の種目並び順の既定として用いる（11 章 M-6 案）。
- 投入データはアセットの JSON ではなくソース内の定数配列として持つ。件数が固定で変更予定がないため。

### 2.7 マイグレーション方針

- 初回リリースは `version = 1`。破壊的な再作成（`fallbackToDestructiveMigration`）は使用しない。ローカル保存のみでバックアップ手段が CSV 出力しかないため、データ消失を許容できない。
- 以降のスキーマ変更は必ず `Migration` を記述する。Room のスキーマ JSON をリポジトリに含め、差分をレビュー対象とする。

## 3. ドメインロジック設計

### 3.1 日付と「当日」の判定

- 「当日」は端末のローカルタイムゾーンにおける現在日付（`LocalDate.now()`）とする。編集可否は対象レコードの `epoch_day` と当日の一致で判定する（要件 4.3.1）。
- 画面を開いたまま日付が変わる場合があるため、編集可否は画面表示時に一度だけ判定するのではなく、保存操作の直前にも再判定する。過去日になっていた場合は保存を行わず、その旨を通知する。

### 3.2 総ボリュームの算出

要件 4.8 に従い、整数演算で算出する。

| 種別 | 式（0.1 kg 単位の整数） |
|---|---|
| 筋トレ・自重フラグなし | `Σ (weight_dg × reps)` |
| 筋トレ・自重フラグあり | `Σ (解決した体重_dg × reps)` |
| 有酸素 | 算出しない。集計対象外 |

- 判定に用いる自重フラグは `snapshot_is_bodyweight`（記録時点の値）である。
- 算出結果は kg 単位に直すと 0.1 kg 単位の小数となる。表示桁は 11 章 M-15 案で定める。
- 算出結果は保存しない。表示・集計のたびに算出する（要件 4.8）。

#### 3.2.1 自重種目に用いる体重の解決

要件 4.8 の順序をそのまま実装する。

1. 対象日に体重記録があれば、その日の全記録の平均を用いる。
2. なければ、対象日より前で体重記録が存在する直近の日を探し、その日の全記録の平均を用いる。
3. 過去に一度も記録がなければ総ボリュームを 0 とする。

実装上の注意点は次のとおり。

- 対象日より後の記録は参照しない。過去日の総ボリュームが未来の記録で変動しないようにする。
- 期間集計やグラフでは日ごとにこの解決を行う。1 日 1 クエリを繰り返すのではなく、対象期間の体重を日付昇順で一括取得し、日付をキーに走査して解決する。期間の開始日より前の直近 1 日分も同時に取得する。
- 平均値の丸めは 11 章 M-14 案で定める。

### 3.3 種目の累計使用回数

- 要件 4.1 に従い、`exercise_record` の件数を `exercise_id` ごとに数える。セット数には依存しない。
- 記録の削除で行が消えるため、集計値は自動的に減る。カウンタ列を持たない。
- 削除済み種目は種目選択画面の一覧に出さないため、集計対象から除外する。ただし種目別グラフの選択肢では削除済みも扱う（要件 4.9.1）。
- 同数の種目の並び順は 11 章 M-19 案で定める。

### 3.4 期間サマリーの集計

- 期間内の全セットを、`snapshot_body_part` ごとに 3.2 の式で合計する（要件 4.10）。
- 部位は記録時点のスナップショットで判定する。マスタの部位を変えても過去の内訳は変わらない。
- 有酸素の種目記録は集計から除外する。
- 週の始まりは日曜日とする。週の範囲は「日曜日から土曜日まで」の 7 日間とする。

### 3.5 種目の削除・区分変更に伴う波及

Repository の単一トランザクションで以下をまとめて実行する。

| 操作 | 波及処理 |
|---|---|
| 種目の削除 | `exercise.is_deleted = 1` に更新し、その種目を参照する全 `template_item` を削除する |
| 種目の区分変更 | `exercise.category` を更新し、その種目を参照する全 `template_item` を削除する |
| 種目名・部位・自重フラグの変更 | マスタのみ更新する。テンプレートと過去記録は変更しない |

- いずれの場合も過去の記録行には触れない（要件 3.4）。
- テンプレート内の種目が 0 件になった場合の扱いは 11 章 M-18 案で定める。

## 4. 休憩タイマー設計

### 4.1 状態モデル

タイマーの状態は `rest_timer` テーブルの行の有無で表現する。

| 状態 | 表現 |
|---|---|
| 停止中 | `rest_timer` に行がない |
| 計測中 | `rest_timer` に 1 行あり、経過秒 = 現在時刻 − `started_at_millis` |

- 表示上の経過秒は 1 秒周期の Flow で再計算する。カウンタ値を保存しない。これにより画面を離れても再入時に正しい値を復元できる（要件 4.4.2）。
- 目安秒数に達した後は計測を止める。表示上の経過秒は `target_sec` で頭打ちとする（要件 4.4.1）。

### 4.2 状態遷移

| 契機 | 処理 |
|---|---|
| セットの完了操作 | セットを確定保存する。計測中のタイマーがあれば、その時点の経過秒を対象セットの `rest_sec` へ書き込み、行を削除する。続いて新しいセットを対象とする行を作成し、終了アラームを登録する |
| 目安秒数への到達 | 対象セットの `rest_sec` に `target_sec` を書き込み、行を削除する。通知を表示する |
| 手動停止 | その時点の経過秒を対象セットの `rest_sec` へ書き込み、行を削除する。アラームを解除する |
| 手動リセット | 対象セットの `rest_sec` を NULL のままとし、行を削除する。アラームを解除する。自動で再開しない |
| 対象セットの削除 | CASCADE で行が消える。アラームを解除する |
| アプリ起動時の復元 | 4.3 の復元処理を行う |

- 最終セットを例外扱いしない。完了操作を行えば必ずタイマーが始まり、停止または到達によって休憩時間が記録される（要件 4.4.3）。
- 有酸素の種目記録は「セットの完了」を持たないため、タイマーの契機とならない。
- 休憩時間の手入力の口は設けない（要件 4.4.3）。

### 4.3 バックグラウンドと復元

アプリ起動時（プロセス生成時）に以下を順に判定する。

1. `rest_timer` に行がなければ何もしない。
2. 現在の起動基準時刻と `boot_base_millis` を比較する。許容誤差を超えて異なる場合、端末が再起動したと判定し、対象セットの `rest_sec` を NULL のまま行を削除する（要件 4.4.2）。
3. 経過秒が `target_sec` 以上であれば、`rest_sec = target_sec` を書き込んで行を削除する。通知が発火しなかった場合でもここで確定する（要件 4.4.2）。
4. いずれにも当たらなければ計測中として復元する。

保証範囲は要件 4.4.2 の表に従う。終了通知はアプリ内遷移および他アプリへの切替時に発火させることを目標とし、タスク一覧からの除去後は保証しない。

### 4.4 通知の実装方針

- 通知チャンネルを 1 つ作成する。重要度は音・バイブレーションを伴わない設定とする（要件 4.5）。
- 終了通知は `AlarmManager` の正確なアラームで発火させ、`BroadcastReceiver` が通知を表示し、対象セットへの `rest_sec` 書き込みを行う。
- 通知権限が拒否されている場合も、タイマーの計測と `rest_sec` の記録は通常どおり行う。通知の表示のみを行わない（要件 4.5）。
- 権限の要求タイミングは、初回に休憩タイマーが開始する直前とする案を採る（要件 4.5 は基本設計での決定を認めている）。拒否された場合の再要求は行わず、設定画面から案内する。

### 4.5 設定値

- 目安秒数はアプリ共通の 1 値とし、DataStore に保存する（要件 4.4.4）。範囲は 1〜3600 秒（要件 3.9）。
- 計測中に設定値を変更した場合、進行中のタイマーには適用しない。`rest_timer.target_sec` に開始時点の値を保持しているため、その値で終了する。

### 5.3 画面ごとの構成

#### S-01 今日の記録

| 区画 | 内容 |
|---|---|
| ヘッダ | 当日の日付、当日の総ボリューム、メニュー入口 |
| セッション一覧 | 当日のセッションを作成順に縦に並べる。各セッションはセッション名（未入力時の表示は M-17 案）と、配下の種目記録の一覧を持つ |
| 種目記録 | 種目名・部位を表示する。筋トレはセット行の一覧、有酸素は実施時間を表示する |
| セット行 | セット番号、重量、回数、休憩時間、メモの有無を表示する。未確定の入力行は「完了」操作で確定する |
| 休憩タイマー | 計測中は画面下部に常時表示する。経過時間、目安秒数、停止、リセットを持つ |

- 種目記録の並び替え、セットの並び替えを当日のみ許可する（要件 4.3.1）。操作方法は M-9 案で定める。
- 削除は 3 単位（セット・種目記録・セッション）で行う。種目記録とセッションの削除には確認ダイアログを出す（要件 4.3.2）。

#### S-02 種目選択

- 累計使用回数の降順で並べる（要件 4.1）。削除済み種目は表示しない。
- 部位による絞り込みと、種目名の部分一致検索を持つ。要件に明示はないが、53 件以上の一覧から選ぶ操作を成立させるために設ける（12 章 Q-2 参照）。
- 選択すると、対象セッションの末尾に種目記録を作成して S-01 へ戻る。作成時に種目属性 4 項目をスナップショットとして書き込む。

#### S-03 種目マスタ管理

- 一覧は削除されていない種目を表示する。追加・編集・削除を行う。
- 追加・編集の入力項目は種目名、部位、区分、自重フラグ（要件 3.2）。
- 区分が有酸素の場合、自重フラグは使用しない（要件 3.2）。部位との関係は 12 章 Q-3 の回答による。
- 削除時は、その種目を含むテンプレートから自動で取り除かれること、過去記録は残ることを確認ダイアログで示す。

#### S-04 テンプレート管理

- テンプレートの一覧、作成、編集、削除、適用を行う（要件 4.6）。
- 編集画面では種目の追加・削除・並び替えと、種目ごとのセット数を設定する。有酸素種目はセット数を持たない。
- 適用時は、対象セッションの末尾に種目記録を追記する。既存の記録は残す。同一種目の重複を許す（要件 4.6）。
- 適用によって展開されるのは空の入力欄であり、この時点では `workout_set` を作成しない（要件 4.2、4.6）。

#### S-05 カレンダー

- 月間表示。日付マスには記録の有無を示す印のみを表示する（要件 4.7）。
- 実施日の判定は「筋トレのセットまたは有酸素の記録が 1 件以上ある日」とする。セッションのみで配下が 0 件の日は印を付けない（要件 4.7）。
- 月の切替を持つ。1 か月分の判定は 1 クエリで取得する。

#### S-06 過去記録の参照

- 対象日のセッション・種目記録・セットを S-01 と同じ構成で表示する。
- 編集操作の入口は表示しない。削除の入口のみ表示する（要件 4.3）。
- 過去日への記録追加の可否は 12 章 Q-4 の回答による。

#### S-07 種目別グラフ

- 種目を選択し、日単位の総ボリュームを折れ線で表示する（要件 4.9.1）。
- 集計キーは `exercise_id`。同一日に複数セッションで実施した場合は合算して 1 点とする。
- 選択肢には、過去記録が存在する削除済み種目も含め、削除済みと分かる表示を添える。
- 期間タブは 1 ヶ月・3 ヶ月・1 年・全期間。各期間の起点は M-20 案で定める。

#### S-08 体重

- グラフ表示と一覧表示をタブで切り替える（要件 4.9.2）。
- グラフは同一日の平均値を 1 点として描画する。一覧は同一日の複数件をすべて登録順に表示する。
- 記録の追加では日付を指定できる。過去日の追加を許す（要件 3.8）。
- 編集の可否は要件 3.8 に従い当日分のみとする。ただし「当日」の解釈は 12 章 Q-5 の回答による。削除は日付を問わず可能とする。

#### S-09 期間サマリー

- 週単位・月単位を切り替える。対象期間を前後に移動できる。
- 表示値は総ボリューム合計と、筋トレ 6 部位の内訳（要件 4.10）。実施日数と有酸素合計時間は表示しない。

#### S-10 CSV 書き出し

- 出力範囲として「全期間」と「期間指定」を選ぶ。期間指定は開始日と終了日を選択し、両端を含む（要件 4.11.1）。
- 実行すると 3 ファイルを生成する。完了時のフィードバックは M-8 案で定める。

#### S-11 設定

- 休憩タイマーの目安秒数のみを設定する（要件 4.4.4）。初期値は M-7 案で定める。
- 通知権限が拒否されている場合の案内をここに置く。

### 5.4 入力バリデーション

要件 3.9・3.10 をそのまま実装する。範囲外・最大長超過の値は保存しない。

| 項目 | 制約 |
|---|---|
| 重量 | 0.5〜999.5 kg、0.5 kg 刻み |
| 回数 | 1〜999 回、1 回刻み |
| 有酸素の実施時間 | 1〜999 分、1 分刻み |
| 体重 | 0.1〜999.9 kg、0.1 kg 刻み |
| 休憩タイマーの目安秒数 | 1〜3600 秒、1 秒刻み |
| 種目名・セッション名・テンプレート名 | 各 50 文字以内 |
| セットのメモ | 500 文字以内 |

- 検証はドメイン層の純粋関数として実装し、ViewModel と Repository の双方から呼ぶ。
- 文字数は Kotlin の `String.length`（UTF-16 コードユニット数）ではなく、コードポイント数で数える。絵文字を含む入力で見た目と不一致にならないようにする。
- 入力欄は数値キーボードを既定とし、刻みに合わない値は保存操作の時点でエラーとする。

| 部品 | 用途 |

| 確認ダイアログ | 種目記録・セッションの削除、種目マスタの削除 |
| スナックバー | 保存・削除・CSV 出力の完了通知 |
| 空状態表示 | 記録・グラフ・一覧が 0 件の場合（M-1 案） |
| 数値入力欄 | 刻みと範囲を持つ数値の入力。重量・回数・体重・秒数で共用 |
| 部位チップ | 部位の表示と絞り込み |

## 6. CSV 出力設計

### 6.1 出力処理の流れ

1. 出力範囲（全期間 / 期間指定）を受け取る。
2. 種別ごとに対象データを取得する。筋トレは種目記録単位、有酸素は種目記録単位、体重は記録単位（要件 4.11.2〜4.11.4）。
3. 行を組み立て、エスケープを適用する。
4. UTF-8（BOM 付き）でダウンロードフォルダへ 3 ファイルを書き出す（要件 4.11.1）。
5. 完了をユーザーへ知らせる（M-8 案）。

### 6.2 ファイル名と文字コード

| 種別 | ファイル名 |
|---|---|
| 筋トレ | `strength_YYYYMMDD_HHMMSS.csv` |
| 有酸素 | `cardio_YYYYMMDD_HHMMSS.csv` |
| 体重 | `weight_YYYYMMDD_HHMMSS.csv` |

- 日時は書き出し実行時のローカル時刻とし、3 ファイルで同一の値を用いる。
- 先頭に UTF-8 BOM（`EF BB BF`）を書く。表計算ソフトでの文字化けを避けるため。

### 6.3 書き出し先

- MediaStore の `Downloads` コレクションへ書き出す。保存先を選ばせるダイアログや共有メニューは使わない（要件 4.11.1）。
- ストレージ権限は要求しない（要件 6 章）。

### 6.4 エスケープ規則

- カンマ、ダブルクォート、改行のいずれかを含む値はダブルクォートで囲む。
- 値内のダブルクォートは 2 つ重ねる。
- 日付は `YYYY-MM-DD` 形式で出力する。
- 改行コードは CRLF とする案を採る（要件に定めがないため 12 章 Q-6 で確認する）。

### 6.5 列構成

要件 4.11.2〜4.11.4 の定義をそのまま実装する。

| ファイル | 列 |
|---|---|
| 筋トレ | 日付、セッション名、種目、部位、セット数、セット詳細 |
| 有酸素 | 日付、セッション名、種目、実施時間 |
| 体重 | 日付、体重 |

- セット詳細は `重量x回数` を `; ` で連結する（例: `60x10; 65x8`）。自重種目は重量を省き `x10; x8` とする。
- 重量の表記桁は画面表示と同じ規則に揃える（M-4 案）。
- 種目名・部位は記録時点のスナップショットを用いる。
- 休憩時間、メモ、総ボリュームは出力しない。
- ヘッダー行の見出し文字列は日本語表記とする（要件の列名をそのまま用いる）。
- 対象データが 0 件の場合の扱いは M-13 案で定める。行の並び順は M-12 案で定める。

## 11. 未決定事項に対する設計案

要件定義書 9.3 のミディアム項目について、以下を案として提示する。いずれも依頼者の承認をもって確定とする。

| No | 項目 | 設計案 | 理由 |
|---|---|---|---|
| M-1 | 0 件時の表示 | 中央に説明文と、可能なら操作への導線を置く。文言案は「まだ記録がありません」「対象期間に記録がありません」「体重の記録がありません」 | 空白画面で操作先を見失わないようにする |
| M-2 | グラフの軸表現 | Y 軸は 0 起点、上限は最大値を切りのよい値へ切り上げ、目盛は 5 分割。単位は kg、整数表示 | 総ボリュームは桁が大きく、小数の情報量が乏しい |
| M-3 | 日付の表示形式 | 見出しは `2026年9月5日(金)`、一覧・グラフ軸は `9/5` | 見出しは曜日が有用、一覧は横幅を優先 |
| M-4 | 重量の表示形式 | 小数部が 0 のときは整数（`60`）、それ以外は小数第 1 位（`62.5`） | 0.5 刻みのため冗長な `.0` を避ける |
| M-5 | タイマーの表示形式 | 計測中・記録表示ともに `mm:ss`（例 `01:30`） | 表示形式を 1 つに統一する |
| M-6 | 初期種目の並び順 | 累計使用回数 0 の種目は種目マスタ ID の昇順とする。初期状態では付録 A の記載順になる | 部位ごとにまとまり、探しやすい |
| M-7 | 目安秒数の初期値 | 90 秒 | 一般的な中量高回数の休憩時間 |
| M-8 | CSV 完了時の表示 | スナックバーで「3 件のファイルをダウンロードに保存しました」と表示し、ファイル名を併記する。絶対パスは表示しない | パス文字列は端末により長く、可読性が低い |
| M-9 | 並び替えの操作方法 | 上下移動ボタン方式 | ドラッグより実装と操作の確実性が高く、縦スクロールと競合しない |
| M-10 | 大画面端末 | 最適化しない。スマートフォンの縦レイアウトを拡大して表示する | 利用者 1 名、対象端末が限定される |
| M-11 | 想定データ規模 | 5 年分・1 日 2 セッション・1 セッション 8 種目・1 種目 5 セットを上限想定（セット約 15 万行）。保持期間の上限は設けない | 索引設計とクエリ方式の妥当性判断のため |
| M-12 | CSV の並び順 | 日付昇順、同一日はセッションの作成順、セッション内は種目の並び順、セット詳細はセットの並び順 | 時系列で読み下せる |
| M-13 | 対象 0 件時の CSV | 0 件でもヘッダー行のみのファイルを 3 つ生成する | 出力結果の構成を常に一定にする |
| M-14 | 体重平均の丸め | 平均値を 0.1 kg 単位へ四捨五入してから総ボリューム算出に用いる | 入力刻みと同じ精度に揃え、整数演算を保つ |
| M-15 | 総ボリュームの表示精度 | 小数第 1 位まで表示する | 0.1 kg 単位の内部表現と一致する |
| M-16 | タイマーの日付跨ぎ | タイマーは対象セットに紐づくため日付を跨いでも継続する。休憩時間はそのまま記録する。タイマーによる `rest_sec` の書き込みは、過去日編集禁止の対象外とする | 記録日ではなく計測の連続性で判断する |
| M-17 | セッション未命名時の表示 | `セッション1`、`セッション2` のように、その日の中での連番で表示する | 日をまたいで番号が増え続けない |
| M-18 | 空になったテンプレート | 空のまま残す。一覧では種目 0 件と分かる表示にする | 利用者が意図せずテンプレートを失わない |
| M-19 | 同順位の種目の並び順 | 種目マスタ ID の昇順（M-6 と同じ規則） | 並び順が実行のたびに変わらない |
| M-20 | 期間タブの起点 | 今日を終端とする直近 N 期間とする。1 ヶ月は今日を含む過去 1 ヶ月、3 ヶ月・1 年も同様 | 直近の推移を見る用途に合う |

## 12. 新規の確認事項

設計中に判明した、要件定義書に定義がなく設計側で仮置きすべきでない事項を挙げる。要件定義書 0.3 に従い、依頼者の回答を得てから確定させる。

| No | 重要度 | 項目 | 内容 |
|---|---|---|---|
| Q-1 | ハイ | 画面の到達手段 | 要件 5 章は画面の一覧のみを定めており、画面間の移動手段（ボトムナビゲーションの採否と項目、管理系画面の入口）が未定義である。5.2 の構成で問題ないか確認したい |
| Q-2 | ミディアム | 種目選択の絞り込み | 種目選択画面での部位絞り込みと名称検索の要否。初期 53 件に追加が重なると一覧が長くなる |
| Q-3 | ハイ | 区分と部位の関係 | 区分が「有酸素」の種目に、部位「有酸素」以外を設定できるか。逆に区分が「筋トレ」の種目に部位「有酸素」を設定できるか。要件 3.3 は用途を示すのみで制約を明示していない |
| Q-4 | クリティカル | 過去日への記録追加 | 要件 4.3.1 は過去日の「編集」を禁じているが、過去日にセッションや種目記録を新規追加できるかは未定義である。体重は過去日の追加が明示的に可能なため、記録側の扱いを確認したい |
| Q-5 | ハイ | 体重編集の「当日」 | 要件 3.8 の「当日に記録した分のみ編集可能」が、記録日が当日のものを指すのか、入力操作を当日に行ったものを指すのかが定まらない。過去日を指定して当日入力した記録の扱いが変わる |
| Q-6 | ミディアム | CSV の改行コード | CRLF と LF のどちらとするか。要件 4.11.1 に定めがない |
| Q-7 | ミディアム | セッションの作成タイミング | 種目を追加する際、セッションが 0 件の日に自動でセッションを作るか、利用者が明示的に作成するか |
| Q-8 | ミディアム | グラフ描画の実現方式 | 外部ライブラリを用いるか、Compose の Canvas で自前描画するか。オフライン専用のため依存を増やさない自前描画を推すが、依頼者の方針を確認したい |
| Q-9 | ミディアム | テンプレートの適用先 | 適用先セッションが複数存在する日に、どのセッションへ追記するかの選択方法 |
| Q-10 | ミディアム | 削除済み種目の表示 | 種目別グラフの選択肢で削除済みと示す表現（末尾に「（削除済み）」を添えるなど） |
